# QA — lobby (메인 화면 → 로비 → 방 → 대기실 → 대국 시작 상태 동기화)

담당: lobby · 포트 3102(서버) / 5102(vite) · DB `/tmp/qa-launch-lobby/majak.db`
스크린샷: `/tmp/qa-launch-lobby/shots/`
테스트 스크립트: `/tmp/qa-launch-lobby/t5_room_flow.mjs` ~ `t11_bots.mjs` (Playwright, 실제 여러 브라우저 컨텍스트로 실행)

## 0. 구조 확인 — 조사 범위 재정의

`packages/server/src/RoomManager.ts`, 클라이언트 홈 화면(`packages/client/src/App.tsx`)을 읽고 실제로 로그인해 확인한 결과,
**이 게임에는 공개 방 목록(로비 리스트)이 없다.** 홈 화면(`03_home.png`)에는 "방 만들기"와 "방 코드 입력 (예: AB3XK7)" 두
길만 있고, 서버 어디에도 전체 방 목록을 방송하는 메시지 타입이 없다(`RoomManager.ts`에 `broadcastLobby`는 **그 방 안**의
좌석 정보만 그 방 참가자들에게 보내는 함수이지, 전체 방 목록이 아니다). 즉 BRIEF가 우려한 "방 목록이 실시간으로 맞는가 —
유령 방" 시나리오는 **이 아키텍처에 존재하지 않는다** — 방은 6자리 코드로만 발견되므로 목록 동기화 버그 자체가 성립하지 않는다.
같은 이유로 "방 이름/비밀방에 특수문자 삽입"도 해당 없음 — 방에는 이름도 비밀번호도 없고 서버가 발급하는 6자 코드뿐이다.

또한 `spectate`는 서버 코드상 관리자 전용이다(`RoomManager.ts:4471` `if (!user.isAdmin) return this.fail(conn, "FORBIDDEN", ...)`).
일반 플레이어가 겪는 "관전 입장·관전 중 인원 변동" 시나리오는 실질적으로 존재하지 않는다(관리자 관전은 이번 라운드 범위 밖으로 판단).

최근 커밋 #425~#429(클라 레이아웃·손패 로딩·봉인 규칙)는 인게임 렌더링·증강 규칙 변경이며, `RoomManager.ts`의 대기실/좌석
상태 기계나 클라이언트의 대기실 컴포넌트와는 겹치지 않는다 — 로비 축과 **관련없음 확인**.

## 확정 — 로비 통계(전적) 갱신 타이밍 (추가 검증, 이 절만 재조사)

### [해당없음] 로비 통계는 대국 종료 직후(수십 ms) 반영되며, 홈 화면은 자동으로 다시 조회한다 — 문제 없음
- 위치: `packages/server/src/RoomManager.ts` (`onGameOver` → `finishStats`, `statsRequest` 핸들러 2274행), `packages/client/src/App.tsx` (`refreshHome()` 4311행 부근, `returnHome()` 끝에서 `refreshHome()` 호출, 로그인 직후에도 4497행에서 `statsRequest` 자동 발신).
- 증상 없음 확인: "방금 둔 판이 왜 전적에 없냐"는 사용자 문의가 나올 만한 지연이 실측상 없다.
- 재현/근거: `/tmp/qa-launch-lobby/stats_timing.mjs` — 원시 WebSocket으로 (1) 계정 생성 → 방 생성 → 봇 3명 채우기 → 시작 → 곧바로 `leaveRoom`으로 좌석을 봇 자동진행에 넘김(서버 로그: `사람이 모두 나갔다 — 봇이 판을 마저 두고 기록한다`) → (2) **같은 계정의 두 번째 연결**로 2초 간격 `statsRequest`를 반복 발사해 응답을 시각 찍었다.
  - 서버 로그: `[room 9D6K4X] 게임 종료 — 1위 Bot_p2(44500), ...` @ `01:25:40.165Z`
  - 그다음 `statsRequest` 응답이 `games:1`을 반영한 시각: `01:25:40.175Z` — **격차 10ms**.
  - 즉 `finishStats`의 `await this.statsStore.record(...)`가 게임 종료 처리 자체에 동기적으로 물려 있어, 그 로그 줄이 찍힌 시점이면 이미 디스크에 반영이 끝난 뒤다. 조회는 폴링이 아니라 **요청-응답(statsRequest)** 방식이라 별도의 "동기화 주기" 지연이 없다.
  - 클라이언트 쪽도 확인: `returnHome()`(결과 화면에서 "홈으로")과 로그인 직후 모두 자동으로 `statsRequest`를 보낸다(`App.tsx:4497`, `refreshHome()` 내부) — 사용자가 수동으로 "↻"를 누를 필요 없이 홈으로 돌아오는 것만으로 방금 끝난 판이 반영된 전적을 받는다.
- 판정: **확정** — 문제 없음. 갱신은 즉시(≈10ms)이고, 정상적인 "판 끝 → 홈" 동선에서 자동으로 다시 조회되므로 사용자가 갱신 지연을 체감할 자리가 없다.
- 부가 관찰(참고, 별도 이슈 아님): 같은 계정으로 두 번째 WS 연결을 열자 첫 번째 연결이 `SESSION_TAKEOVER`로 끊겼다 — 이전 라운드에서 이미 확정한 "같은 계정 두 탭" 동작과 동일하고 의도된 것이다(재확인, 새 문제 아님).

## 환경 메모 (이번 라운드 진행상 특기사항 — 남 몫에 영향 없음)
- 조사 초반, 같은 브리핑을 받은 것으로 보이는 배경 프로세스(`lobby_qa2.ts`)가 **같은 포트 3102**에서 나와 동시에 계정을 만들고 있어 로그가 섞였다. PID로 찾아 종료(`kill -9`)하고 DB를 지운 뒤 재시작해 격리를 회복했다.
- 이후 작업 중 내가 띄운 서버(3102)가 외부 SIGTERM으로 두 차례 재시작됨(공유 환경의 다른 세션이 프로세스를 정리한 것으로 보임 — 포트 3011 공개 서버와는 무관, 내 격리 DB/포트에만 영향). 매번 같은 DB로 재시작해 데이터는 보존됐고, 테스트는 계속 진행했다.
