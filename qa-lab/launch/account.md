# 계정·인증 QA (담당: account)

환경: 서버 포트 3101, vite 5101, DB `/tmp/qa-launch-account/*.db`. 검증 방식:
node 내장 `WebSocket`으로 실제 WS 프로토콜(`register`/`login`/`tokenLogin`/
`changePassword` 등)을 직접 쏘는 스크립트(`/tmp/qa-launch-account/wsclient2.mjs`,
`pwtest2.mjs`, `pwtest3.mjs`)와, vite로 띄운 실제 클라이언트를 브라우저로 조작한
것 둘 다 사용. `docs/15_ACCOUNTS_SITE.md`·`SiteDb.ts`·`RoomManager.ts`(인증 부분)·
`App.tsx`(랜딩/인증 화면)를 코드로 대조했다.

### [P3] 앞뒤 공백 닉네임이 조용히 trim되어 가입된다 — 안내 없음
- 위치: `packages/server/src/RoomManager.ts:1846` (`db.register(username.trim(), ...)`)
- 증상: `" leadspace"`(앞 공백)·`"trailspace "`(뒤 공백)로 가입하면 거절되지 않고
  공백이 조용히 제거된 `"leadspace"`/`"trailspace"`로 가입된다. 사용자는 자기가
  입력한 문자열 그대로 계정이 만들어졌다고 믿을 수 있다(붙여넣기로 흔히 생김).
  내부에 공백이 있는 경우(`"spa ce"`)는 정규식에 걸려 거절된다 — 앞뒤와 내부가
  다르게 처리된다는 점도 일관성이 없다.
- 재현:
  ```
  {"type":"register","username":" leadspace","password":"password123"}
  → authOk { username: "leadspace" }   // 입력한 이름과 다르게 저장됨
  ```
- 판정: 확정 (코드 인용 + WS 실측)
- 제안: 사소하지만, 가입 폼에서 trim된 최종 닉네임을 제출 전에 미리보기로
  보여주거나, 클라이언트에서 자체적으로 trim 후 전송해 서버 응답과 입력이
  어긋나지 않게 한다. `SiteDb.register`/`usernameProblem` 자체를 바꿀 필요는 없음
  (기존 계정 호환에 영향 없어야 함).

### [P3] 인증 응답이 요청 순서와 다르게 도착할 수 있다 (연속 로그인 시도 시)
- 위치: `packages/server/src/RoomManager.ts` `doAuth`(scrypt 비동기) +
  `authAttempts` 레이트리밋 카운터
- 증상: 한 연결에서 로그인 요청을 연속으로 여러 번(레이트리밋 한도 초과분 포함)
  쏘면, 한도 초과로 즉시 거부되는 `RATE_LIMITED` 응답(동기, scrypt 없음)이
  아직 scrypt 계산 중인 앞선 요청들의 `LOGIN_FAILED` 응답보다 **먼저** 도착한다.
  레이트리밋 판정 자체는 정확하다(15회 중 12회 통과·3회 초과 거부, 카운트도
  올바름) — 다만 응답 도착 **순서**가 요청 순서와 어긋난다.
- 재현: `/tmp/qa-launch-account/full_ratelimit.json` (한 연결에서 `login` 15회
  연속 전송, 순서 무관 응답 확인). 실제 실행 로그:
  ```
  1 RATE_LIMITED
  2 RATE_LIMITED
  3 RATE_LIMITED
  4 LOGIN_FAILED
  ...
  15 LOGIN_FAILED
  ```
  (요청은 1~15 순서로 보냈지만 뒤쪽 요청 3개의 거부가 먼저 도착)
- 판정: 확정 (실측). 다만 실제 로그인 폼은 한 번에 한 요청만 보내고 응답을
  기다리므로 **UI로는 재현되지 않는다** — 프로토콜에 요청-응답 상관 ID가 없는
  상태에서 클라이언트가 나중에 다중 동시 요청(예: 이중 클릭 방지가 없는 다른
  버튼)을 붙이면 같은 함정에 빠질 수 있다는 기록성 이슈.
- 제안: 지금 당장 고칠 필요는 낮음. 향후 요청-응답 상관관계가 필요한 기능을
  추가할 때 이 특성을 기억해 둘 것.

- 로그인 대소문자 무시(NOCASE), 레이트리밋(연결당 12/분) 정상 동작
- `SIGNUP_CODE` 가입 게이트 정상 동작(없음/오답/정답 3가지 모두)
- 관리자 코드 가입 성공 시 회전(1회용) 정상 동작
- **비밀번호 변경 시 다른 세션 전부 무효화 + 열린 소켓 강제 종료** (M-3 해결 확정)
- 같은 토큰으로 다중 소켓 접속 시 `SESSION_TAKEOVER`로 먼저 접속 종료, 클라이언트가
  재연결 핑퐁 없이 안전하게 처리(2026-08-25 "한 계정 한 창" 정책)
- 닉네임을 통한 XSS는 서버 문자셋 제한 + 클라이언트 미사용(dangerouslySetInnerHTML 없음)으로 구조적으로 불가능
- 닉네임 변경 기능 자체가 없음(미구현, 버그 아님) — 검증 대상 없음
- 게스트 → 계정 전환 시 전적 유실/중복: 게스트 판은 애초에 아무것도 기록하지 않아 이관할 데이터가 없음
- 인증 관련 문자열 필드 길이 상한(`withinAuthFieldLimit`)이 거대 페이로드로 인한 scrypt/DB 남용을 입구에서 차단
- `changePassword`에 대한 타입 검증 누락 시 서버 크래시 여지 없음(문자열 타입 가드 있음)
- 인증 실패 시 서버가 던지는 오류 메시지는 전부 사람이 읽는 한국어 문장(원문 스택트레이스·영어·빈 화면 없음), 클라이언트 회원가입 화면에 비밀번호 규칙이 실제로 적혀 있음(고급 설정 통해 로컬 서버 3101 연결 후 브라우저로 직접 확인)
