# A. 구조적 버그

## A-1. 정산 순서가 드래프트 픽 순서로 결정된다 (근본 원인)

`EffectRegistry.matching()`은 `(layer, priority, 등록 seq)`로 정렬한다. 그런데

- **티어가 아직 혼재한다**: silver 5 / gold 16 / prism 83.
  (docs/10 §2는 "신규 증강은 전부 prism"이라고 했지만 21종이 옛 티어 그대로다.
  티어는 이제 표시용이 아니라 **인터셉터 실행 순서 그 자체**다.)
- 같은 prism끼리는 `seq` = **installAugment 호출 순서** = **드래프트 픽 순서**로 갈린다.

`ROUND_SETTLED`를 가로채 `deltas`를 고쳐 쓰는 증강이 **17종**이다
(all_or_nothing · always_tenpai · blame_shift · blood_contract · counter · devils_advance ·
die_hard · eternal_dealer · hourglass · jackpot · karma · let_it_ride · nagashi_yakuman ·
parasite · scapegoat · spy · yakuman_shield + addWinPointBonus 계열 8종).
이들은 전부 "현재 deltas를 읽어 고쳐 쓴다" — **교환법칙이 성립하지 않는다.**

### 실측 A-1a — 기생충 × 일확천금

p0가 론 화료(3900), p0는 일확천금 3배, p2는 p0에 기생(획득의 절반 강탈).

```
기생충 먼저 설치 : {p0: 5700, p1: -3900, p2: 2000, p3: 0}   ← 합계  3800
일확천금 먼저    : {p0: 5800, p1: -3900, p2: 5900, p3: 0}   ← 합계  7800
```

p2의 수익이 **2000 vs 5900 (약 3배)**. 뱅크 발행액도 3800 vs 7800으로 2배 차이.
같은 패·같은 시드·같은 증강인데 **누가 먼저 드래프트에서 픽했는가**만으로 갈린다.

### 실측 A-1b — 승승장구 × 유국역만 (같은 사람)

```
승승장구 → 유국역만 : {p0: 51000, p1: -15000, p2: -15000, p3: -21000}
유국역만 → 승승장구 : {p0: 55000, p1: -17000, p2: -17000, p3: -21000}
```

### ✅ 수정 (60차)

정산 인터셉터의 순서를 tier에서 완전히 떼어냈다. 전부 하나의 `SETTLE_LAYER`에 모으고
**단계(priority)로만** 순서를 정한다 — 계약과 단계 정의는 core `augment/settleStages.ts`,
등록 경로는 content `util.settleInterceptor` 하나뿐이다. 설계 서술은 **docs/10 §7.1**.

```
Replace → Redistribute → Multiply → BankTopUp → Transfer → DrawPatch → Shield → Observe
```

수정 후 실측 — **두 순서가 완전히 동일**:

```
기생충 먼저 / 일확천금 먼저 : {p0: 5800, p1: -3900, p2: 5900, p3: 0}   (양쪽 같음)
```

tier는 그대로 남겨 뒀다(다른 규칙 합성에서 아직 의미가 있다). 정산 순서만 tier와 무관해졌으므로
"silver/gold 21종을 prism으로 통일"은 더 이상 급한 일이 아니다.

## A-2. 역만 방어술이 책임전가 앞에서 한 번도 발동하지 않는다

**증상**: 역만 방어술 보유자가 역만을 정통으로 맞는다. 텍스트("역만 피해에 **완전 면역**,
횟수 제한 없음")가 거짓이 된다.

**실측** — p0 국사무쌍 론(48000, from p1), p0는 책임전가, p2는 역만 방어술:

```
방어막 먼저 설치 : {p0: 48000, p1: -16000, p2: -16000, p3: -16000}
책임전가 먼저    : {p0: 48000, p1: -16000, p2: -16000, p3: -16000}
대조군(방어막만) : {p0: 48000, p1: -48000, p2: 0,      p3: 0}
```

**두 순서 모두 p2가 −16000.** 방어가 0회 발동했다.

**원인**: `yakuman_shield`는 **gold(200)**, `blame_shift`는 **prism(300)**.
레이어가 다르므로 설치 순서와 무관하게 **항상 방어막이 먼저** 돈다. 그 시점의
`deltas[p2]`는 0이라 발동 조건(`loss < 0`)을 만족하지 않아 통과하고, 그 뒤 책임전가가
p2에게 −16000을 **새로** 부과한다. 방어막은 두 번 돌지 않는다.

같은 구조로 **덤터기(gold, 쯔모 지불을 한 명에게 몰기)** 도 역만 방어막을 우회한다.

### ✅ 수정 (60차)

`blame_shift`·`scapegoat`을 `Redistribute`(100), `yakuman_shield`를 `Shield`(600) —
**방어는 반드시 마지막**으로 못 박았다. 어떤 경로로 생긴 손실이든 최종값을 보고 막는다.

수정 후 실측 (p0 국사 론 48000, p0=책임전가, p2=역만 방어술):

```
방어막 먼저 / 책임전가 먼저 : {p0: 32000, p1: -16000, p2: 0, p3: -16000}   (양쪽 같음)
```

p2의 손실이 **정확히 0** — 책임전가로 새로 부과된 지불까지 전액 환급된다.
나머지 두 명은 3분할된 몫을 그대로 내고, 환급분은 화료자 이득에서 차감된다(48000 → 32000).

## A-3. 승승장구의 '노텐' 판정이 delta 부호 추정이라 오염된다

`always_tenpai`는 유국 정산에서 **`deltas[id] < 0`인 사람을 노텐 지불자로 간주**해
1인당 2000을 더 받는다. 그런데 다른 유국 증강이 먼저 돌아 음수를 만들면 **텐파이였던
사람까지 노텐으로 오판**한다.

**실측** — p1·p2는 진짜 텐파이, p3만 노텐:

```
대조군           : {p0: 1000,  p1: 1000,   p2: 1000,   p3: -3000}
승승장구만       : {p0: 3000,  p1: 1000,   p2: 1000,   p3: -5000}   ← 정상(+2000)
유국역만 → 승승장구: {p0: 55000, p1: -17000, p2: -17000, p3: -21000}  ← p1·p2에게서 2000씩 더 뜯음
승승장구 → 유국역만: {p0: 51000, p1: -15000, p2: -15000, p3: -21000}  ← 정상
```

### ✅ 수정 (60차)

`RoundSettledPayload.tenpaiPlayers`를 추가했다 — `sys.settleDraw`가 이미 계산하는 텐파이
집계(`draw.treatAsTenpai` 포함)를 payload에 그대로 싣는다. 승승장구는 부호 추정을 버리고
이 목록만 본다(필드가 없던 구 리플레이는 예전 추정으로 폴백).

수정 후 실측 — 두 순서 동일하고, 노텐 보너스는 **실제 노텐 1명분(+2000)만** 붙는다:

```
승승장구 → 유국역만 / 유국역만 → 승승장구 : {p0: 51000, p1: -15000, p2: -15000, p3: -21000}
```

**교훈**: 정산 payload에 판정 근거가 없으면 **payload를 늘린다.** 부호·금액으로 상태를
추정하는 코드는 다른 증강이 같은 필드를 건드리는 순간 반드시 깨진다.

## A-4. 무장해제 × 진짜 용 = 그 국이 통째로 삭제된다 (하드락)

**실측** — p0가 진짜 용, 손패 17장 5멘쯔 1작두(완성형):

```
무장해제 전 : 손패 17 · win validate = null                  ← 화료 가능
무장해제 후 : 손패 17 · scoring.totalSets = 4 · win validate = "not a winning hand"
              discard validate = null                        ← 버릴 수는 있다(→ 16장)
```

무장해제는 `deal.handSize`(이미 나눠 준 16장은 되돌리지 않는다)와 `scoring.totalSets`
모디파이어를 **국이 끝날 때까지** 꺼 버린다. 결과적으로

- 손패는 **16/17장인데** 화료형은 **4멘쯔+작두(14장)** 를 요구한다 → 수학적으로 성립 불가.
- 화료·텐파이·리치·후리텐 판정이 전부 같은 경로(`scoringOptionsOf`)를 타므로 **전부 죽는다.**
- 그 국 내내 회복 수단이 없다.

진짜 용의 `conflicts`는 **드래프트 제시만** 막는다. 무장해제는 상대 증강을 지목하는
방식이라 conflicts로 막을 수 없다.

### ✅ 수정 (60차) — 배제가 아니라 "진짜 무장해제"로

대상에서 빼는 대신, 무장해제가 **물리 상태까지 되돌리게** 했다.
무장해제는 잠그기 **직전에** `AugmentDisarmed`를 먼저 내고(순서가 계약), 대상 증강이 그
이벤트에 반응해 스스로 원상복구한다. 진짜 용은 손패에서 **가장 쓸모없는 3장**을
**패산 맨 밑**으로 반납해 13/14장으로 돌아온다 — 용은 풀리지만 그 국을 계속 싸울 수 있다.

수정 후 실측:

```
무장해제 후 : 손패 14 · 패산 +3 · 바닥 변화 없음 · scoring.totalSets = 4
              → 4멘쯔 기준으로 텐파이/화료 판정 성립 (하드락 없음)
```

- 바닥이 아니라 패산으로 보내는 이유: 버림패로 가면 없던 방총·후리텐이 생기고
  `discardedKinds`가 오염된다. 배패에서 3장을 더 받은 것이므로 패산에 돌려주면
  그 국의 총 쯔모 수도 표준으로 정확히 복원된다.
- 반납 3장 선정은 **결정적**이다(같은 패 수 3점 · 슌쯔 이웃 ±1 → 2점 / ±2 → 1점,
  동점은 kindKey → tileId). 쯔모패는 후보에서 빼 "14번째 패" 불변식을 지킨다.
- 국 시작 시점에 물리 상태를 확정하는 **새 증강은 `AUGMENT_DISARMED` 반응을 함께 구현**한다
  (docs/10 §7.2).

## A-5. 진짜 용의 conflicts 누락 2건

진짜 용은 6종(open_kokushi·giant_god·royal_kokushi·async_chiitoi·mixed_nine_gates·void_kan)을
상호 배제하고 있는데, **같은 이유로 죽는 증강 2종이 빠져 있다.**

### A-5a. 절벽 위에 피어난 꽃 (cliff_bloom) — 완전 무효

`cliff_bloom.ts:133-136`

```ts
const sets = 4 - meldCountOf(state, holder);   // ← 4 하드코딩
if (concealed.length !== sets * 3 + 2) return null;
```

**실측**:
```
진짜용=false 손패=14 | 요구 sets*3+2=14 | 일치=true
진짜용=true  손패=17 | 요구 sets*3+2=14 | 일치=false
```

진짜 용 보유자는 손패가 16/17이라 **이 조건을 영원히 만족할 수 없다** →
"만개"(확정 화료형 재구성)가 한 번도 일어나지 않는다. 깡을 하고 액티브를 눌러도 조용히
아무 일도 안 생긴다.

### A-5b. 밑장빼기 (bottom_deal) — 대기 계산이 틀린다

`bottom_deal.ts:147`

```ts
const waits = new Set(winningKinds(handKinds, meldCount).map(kindKey));  // ← opts 없음
```

`scoringOptionsOf(state, rules, holder)`를 넘기지 않아 **항상 4멘쯔 기준**으로 대기를 센다.
진짜 용 보유자에게는 잘못된 대기 집합이 나온다. (액션 validate 자체는 통과 —
실측 `bottom_deal validate = null` — 그래서 조용히 틀린다.)

### ✅ 수정 (60차) — 배제가 아니라 공존

`conflicts`에 추가하지 않았다. **죽는 쪽을 고쳐서 함께 작동하게** 했다 — 배제는 픽 하나를
없애는 것이므로 공존시킬 수 있으면 그게 낫다.

- `cliff_bloom`: `sets = (scoringOptionsOf(...).totalSets ?? 4) - meldCount`.
  진짜 용 보유자는 두 번째 깡 후 손패가 14장(16 + 쯔모 − 깡 4 + 영상 1)이 되고
  5멘쯔 기준 `sets*3+2 = 14`와 정확히 맞아 **만개가 그대로 터진다.**
  회귀 테스트가 진짜용 유/무 양쪽에서 "두 번째 안깡 → 만개 → 즉시 화료"를 확인한다.
- `bottom_deal`: 봇 정책이라 `GameState`를 못 봐서 `scoringOptionsOf`를 부를 수 없었다.
  그래서 **`PlayerView.scoringOptions`** 를 신설해(docs/10 §7.3) 뷰어 본인의 분해 옵션을
  실어 보낸다. `winningKinds(kinds, meldCount, undefined, view.scoringOptions)`.
  같은 이유로 `cliff_bloom`의 봇 정책도 함께 고쳤다.

**참고**: `scoringOptionsOf`를 쓰지 않고 텐파이/화료형을 계산하는 파일은
`async_chiitoi` `bottom_deal` `cliff_bloom` `mixed_nine_gates` `royal_kokushi` `siege_riichi`
`wind_lineage` 7종이다. 앞의 4종은 자기가 분해 옵션을 정의하는 쪽이라 문제가 없고,
`siege_riichi`·`wind_lineage`는 규칙만 얹으므로 무해하다. **실제 위험은 위 2종.**

# B. 게임을 부수는 과한 시너지

## B-1. 뚫린 천장 × 판수 증강 = 지수 폭발

`aotenjou_ceiling.ts`

```ts
const effHan = info.han + 13 * info.yakumanCount;
const base = info.fu * 2 ** (2 + effHan);
```

그리고 `standardActions.ts:818`에서 **`info.han = ev.han + extraHan`** 이다 —
`score.extraHan`이 이미 합산돼 들어온다. 즉 **뚫린 천장 아래서는 +1판 = 점수 ×2**다.

**실측** (청일색 량페코 11판 30부 자 론 = 원래 36000 삼배만):

| 조합 | p0 획득 |
|---|---|
| 대조군 | 36,000 |
| 뚫린 천장 | **1,474,600** |
| 뚫린 천장 + 일확천금(3배) | **4,423,800** |
| 진짜 용 단독 (17장 손) | 48,000 |
| **진짜 용 + 뚫린 천장** | **31,457,300** |

진짜 용은 +3판(×8)에 5멘쯔라 부수도 높아져 655배가 된다.

같은 방식으로 배수 증강이 되는 것: `ankan_dora`(밀실의 도라) · `north_trader`(북풍 상인) ·
`no_retreat`(리치·일발 +1, 뒷도라 2배) · `riichi_upgrade`(트리플리치 +2) ·
`counter`(직격 +4판) · `true_dragon`(+3).

**권장**: 뚫린 천장의 보전액에 상한을 되살리거나(48차에 삭제한 32000 캡),
`aotenjouTotal`에서 `info.extraHan`을 빼고 계산한다(증강 판은 상한 안에서만 작동).

## B-2. 천하통일 = 위 전부가 "첫 국 즉시 우승" 버튼이 된다

`unification`은 `match.instantWinScore = 45000`. 한 국 정산 직후 4만 5천을 넘으면 남은 국을
전부 무시하고 게임이 끝난다.

- B-1의 어떤 조합이든 **한 방에 5만을 훨씬 넘는다.**
- 심지어 전투가 아닌 조합에서도 넘는다 — 실측 **유국역만 + 승승장구 = 유국 한 번에 55,000**.
- 뱅크가 발행하는 점수(뚫린 천장·큰손·일확천금·모 아니면 도·카운터)는 상대에게서 뺏는 게
  아니므로 **상대가 막을 방법이 구조적으로 없다.** docs/10 리트머스 ④(대응 가능성) 위반.

**권장**: 천하통일의 문턱 판정에서 **뱅크 발행분을 제외**하거나, 천하통일을

## B-3. 공성계 × 리치 봉인 = 1000점으로 상대 셋의 리치를 국 내내 봉인

**실측** — p0 손패는 완전 무텐파이(`147m258p369s1234z`):

```
riichi validate (공성계 보유) : null          ← 통과
riichi validate (공성계 없음) : "not tenpai after discard"
riichi 선언 후 → 봉인 플래그 : true
p1 riichi.blocked            : true
```

`siege_riichi`가 `riichi.requiresTenpai`를 끄고, `riichi_seal`이 "그 국의 첫 리치"를
잡아 나머지 셋을 봉인한다. **배패 직후 1순에, 아무 손도 없이, 1000점으로**
그 국의 리치를 셋 다 지운다. 매 국 반복 가능(둘 다 상시 패시브).

- **+ 손바닥 뒤집기**를 얹으면 가짜 리치를 취소하고 정상 플레이로 복귀할 수 있다.
  봉인 플래그는 `roundKey` 스코프라 **취소해도 유지**되며, 재리치도 공짜다. 사실상 무비용.
- **+ 물러설 수 없는 선언**이면 공탁 1000도 안 낸다 → 진짜로 공짜.

**권장**: `riichi_seal`의 발동 조건에 "선언 시점에 실제 텐파이"를 넣거나,
`siege_riichi`로 건 리치는 `riichi_seal`의 "첫 리치"로 세지 않는다.

## B-4. 리치 봉인 / 이중 선언이 상대의 리치계 증강을 통째로 무효화한다

`riichi.blocked`가 서면 표준 `riichi` 액션이 거부된다(실측 `"riichi is sealed this round"`).
그 국 동안 **발동 자체가 불가능해지는 증강**:

카운터 · 물러설 수 없는 선언 · 손바닥 뒤집기 · 스텔스 리치 · 승부수 · 이중 선언 ·
한 끗 차이 · 공성계 (8종)

이건 "대응 가능한 방해"가 아니라 **상대의 증강 픽 하나를 매 국 지우는 것**이다.
리치 봉인은 발동 횟수 제한도 없다(매 국 자동).

### 🟡 판정: 의도된 능력 (2026-07-27 사용자 확정)

"다른 증강의 리치까지 못 쓰게 하는 것"이 리치 봉인의 설계 의도다. 그래서 §B-5의
구멍(오픈 리치·모 아니면 도 우회)은 **막는 방향으로** 고쳤다. 지금은 4종 전부 막힌다.

### ✅ 완화 적용 (60차, 2026-07-27 사용자 확정) — **봉인의 대가는 리치를 지고 있는 것**

봉인은 이제 **보유자가 그 리치를 지고 있는 동안만** 유효하다.

- 선제 리치를 걸면 그 순간부터 나머지 셋의 리치가 잠긴다 (기존과 동일).
- **손바닥 뒤집기·승부수로 리치를 풀면 봉인도 그 자리에서 풀린다.**
- 푼 사이에 상대가 리치를 걸었다면, 같은 국에 다시 걸어도 봉인은 돌아오지 않는다
  (더 이상 "선제"가 아니므로).
- 국이 바뀌면 초기화되고, 다음 국에 다시 선제 리치를 걸면 그 국 동안 또 봉인된다.

**구현 — 이벤트 결합 없이 상태에서 파생한다.** 봉인의 현재 유효성은
`isSealActive(state, holder)` 하나로 계산한다:

```
① 이번 국에 봉인을 세웠다 (roundKey 스코프 플래그 = "내 리치가 그 국의 첫 리치였다"는 과거 사실)
② 보유자가 지금도 리치 중이다        ← 풀면 봉인도 풀린다
③ 다른 누구도 리치 중이 아니다       ← 푼 사이 남이 걸었으면 되살아나지 않는다
```

손바닥 뒤집기(`RiichiFlipped`)든 승부수(`RiichiCanceled`)든 결국
`byPlayer[holder].riichi = null`로 끝나므로, **해제 이벤트를 구독하지 않는다.**
새 해제 수단이 생겨도 자동으로 따라온다.

전원 공개 배너도 함께 동기화한다 — 봉인이 풀렸는데 "봉인"이 떠 있으면 상대가 걸 수
있는데도 안 거는 잘못된 대응을 한다(Rule #4는 정보가 **맞을** 때만 산다).

**이것으로 §B-3(공성계 무비용 조합)의 손바닥 뒤집기 변형이 정확히 잘렸다.**
가짜 리치로 봉인만 세우고 취소해 정상 플레이로 돌아가는 길이 막혔고, 정직하게 리치를
지고 싸우는 쪽은 아무것도 잃지 않는다. 공성계 단독 조합(리치를 계속 지고 있으므로
본인도 화료 불가)은 사용자 판정대로 그대로 둔다.

### 검토했으나 적용하지 않은 안

| 안 | 왜 안 했나 |
|----|-----------|
| 횟수 제한 (동풍전 1 · 반장전 2회) | 채택한 "리치 유지" 조건이 이미 실질 비용이라 겹친다 |
| 순 제한 (첫 6순 리치만) | 위와 역할이 겹친다 |
| 1인 지목 (전원 → 한 명) | 리치 봉인이 이중 선언과 거의 같은 증강이 되어 정체성을 흐린다 |

# C. 서로 상쇄되는 조합 (역시너지)

## C-1. 스텔스 리치 × 은닉을 깨는 리치 계열 — ✅ 6종 분리 (2026-08-05 확대)

> 2026-08-05 사용자 지시: **스텔스 리치는 리치를 건다는 게 티가 나는 증강과 같이 나오면 안 된다.**
> 리치 봉인 하나만 막고 있던 것을 아래 두 부류로 넓혔다.
>
> ① 능력으로 리치를 걸면서 그 사실을 전원 공개하는 것 — 상호 무효
>    `open_riichi_reveal`(오름패 공개) · `all_or_nothing`(판돈 공개) ·
>    `soul_strike`(남은 쯔모 공개) · `riichi_seal`(봉인 공개)
> ② 리치 중에만 일어나는 일을 전원 공개하는 것 — 내가 고르지 않아도 터진다
>    `off_by_one`(리치 필수 + 바뀐 패 공개) · `palm_flip`(리치 중 발동 + 해제 공개)
>
> 잠그지 않은 것: `riichi_upgrade`는 스텔스면 홀더 전용 채널로 보낸다(#126에서 그 분기가
> 실제로 돌게 고쳤다). `free_riichi_discard`·`late_double`·`no_retreat`·`siege_riichi`는
> 공개 채널이 없고, `push_riichi`는 남을 리치시키는 것이라 내 은닉과 무관하다.

### (원문) 리치 봉인만 분리하던 시점의 분석

스텔스 리치는 `TILE_DISCARDED { riichi: true, riichiCost: 0 }`을 낸다. 그래서 리치를 감지하는
**다른 내 증강이 그대로 발동하고, 전원 공개 채널로 나를 알린다.**

**실측**:
```
riichi 상태 : {"double":true,"ippatsu":true,"discardIndex":0}
riichi_seal 봉인 플래그 : true
전원 공개 채널 view:*:riichi_seal:p0 : "봉인"
p1 riichi.blocked : true
```

"아무도 내가 리치인 줄 모른다"가 존재 이유인 증강인데, 같은 손의 다른 증강이
**"p0이 리치를 걸었다"를 테이블에 띄운다.** 이중 선언(하가 지목 공개)·카운터(대상 공개)도 동일.

부수적으로 — 1순 스텔스 리치에는 `double: true`가 붙는다(더블리치). 정산에서 갑자기
더블리치 2판이 튀어나오는데 상대는 리치 자체를 몰랐다.

## C-2. 리치 봉인 × 카운터 — 동시 성립이 불가능하다  🟡 유지

- `riichi_seal`: 내 리치 선언 시 **다른 누구도 리치 중이 아니어야** 발동("그 국의 첫 리치").
- `counter`: **상대가 먼저 리치를 건 국**에 내가 추격 리치를 걸어야 발동.

두 조건은 서로 배타적이다. **같은 국에 둘 다 켜지는 경우가 존재하지 않는다** —
어느 국이든 둘 중 하나는 확정적으로 죽은 픽이다.

**🟡 판정: 유지** (2026-07-27 사용자 확정). 국마다 상황이 다르므로 —
내가 먼저 텐파이면 봉인, 상대가 선리치를 걸면 반격 — **국별로 골라 쓰는 조합**으로 본다.
둘 다 상시 패시브라 어느 쪽이 켜질지는 그 국의 전개가 정하고, 플레이어는 "먼저 걸까
기다릴까"를 고를 수 있다.

## C-3. 죽기살기 × 수비 증강

`die_hard`는 **마이너스로 내려간 깊이만큼 부호를 뒤집는다**(−8000 → +8000).
즉 **크게 잃을수록 크게 버는** 구조다. 그런데 같이 들면:

- **천하무적**(그 국 무방총) · **불가침 조약**(론 면역) · **역만 방어술**(역만 실점 0) ·
  **승승장구**(노텐 벌점 면제)

이들은 전부 그 "크게 잃는 순간"을 없앤다. **수비가 성공할수록 죽기살기의 수익이 0에
수렴한다.** 특히 역만 방어술은 죽기살기가 노리는 가장 큰 실점(역만)을 정확히 지운다.

## C-4. 완전 중복 — 두 번째 픽이 아무 일도 안 하는 조합

같은 규칙 키를 같은 값으로 쓰는 쌍(실측 스캔):

| 규칙 키 | 겹치는 증강 | 결과 |
|---|---|---|
| `win.furiten.enabled` + `win.requiresYaku` | 복수자 · 대기만성(반장) · 대기만성(동풍) · (표준 철벽) | 완전 중복 |

`score.extraHan`(밀실의 도라·북풍 상인·물러설 수 없는 선언·이중 선언·진짜 용)만은
**가산**이라 중복이 아니다 — 대신 B-1의 폭발원이다.

### ✅ 무너진 국경 / 동수의 결속 역할 분리 (60차, 사용자 확정)

무너진 국경이 혼색 **슌쯔**와 혼색 **커쯔**를 둘 다 열어서 동수의 결속의 능력 전부를
포함하고 있었다. 이제 갈랐다:

- **무너진 국경** = 무늬 없는 **슌쯔**만 (2만·3통·4삭). `scoring.mixedRuns`. 치도 무늬 무시.
- **동수의 결속** = 무늬 없는 **커쯔**만 (2만·2통·2삭). `scoring.mixedTriplets`. 펑·깡 담당.

둘을 함께 뽑으면 그때 비로소 "랭크만 맞으면 뭐든 몸통"이 완성된다 — 죽은 픽이 **진짜
시너지**로 바뀌었다. 남은 7쌍은 미착수다.

## C-5. 무장해제가 완전 무효인 대상 26종

무장해제는 `RuleRegistry`/`EffectRegistry`의 **source 게이팅**만 한다. 규칙 Modifier도
Interceptor/Reaction도 등록하지 않는 **순수 액션형·역 등록형** 증강에는 아무 효과가 없다.

**실측 면역 26종**:
```
alchemist bluff_pretense bottom_yaku danger_sense even_world frame_up full_hand_swap
genesis giant_god grave_rob meld_dissolve mixed_nine_gates pond_snatch red_five_touch
reload seat_swap silent_pact suit_unify table_flip take_back tanyao_break tenpai_scan
three_dragons_will tile_dyeing tile_split triple_peek
```
(유효한 것은 78종)

그런데 `disarm.ts:108-118`의 후보 목록은 **상대 증강 전부를 필터 없이** 낸다.
동풍전 1회 · 반장전 2회뿐인 발동을 **25% 확률로 통째로 낭비**한다. 봇 정책도
"증강을 가장 많이 든 상대"만 보고 고르므로 이 함정에 그대로 빠진다.

### ✅ 수정 (60차) — 제외가 아니라 게이트 확장

후보를 빼는 대신 **게이트를 액티브 버튼까지 넓혔다.** `installAugment`가
`holderTurnOptions`를 `isSourceDisarmed`로 감싸므로, 잠긴 증강은 후보가 비고
`FlowController.submit`이 제시되지 않은 옵션을 거부한다 — 증강별 수정 없이 26종 전부
실제로 잠긴다. 회귀 테스트는 단색 세계(규칙·효과 0개)로 확인한다.

## C-6. 봉인술사 × 리치 상대

`standardActions.ts:158` — `discard.blockedKinds`는 **리치 중인 플레이어에게는 적용되지
않는다**(리치는 쯔모기리 강제라 소프트락을 피하려고 의도적으로 뺀 가드).
따라서 이미 리치를 건 상대를 지목하면 완전 무효다. 봉인술사의 후보 목록에는 리치 여부
필터가 없다.

# D. 정보 일관성이 깨지는 조합

## D-1. 오픈 리치 × 연금술사 / 염색 — 공개한 오름패가 사후에 바뀐다  🟡 유지

`open_riichi_reveal.ts`의 주석이 전제를 명시하고 있다:

> 리치는 손이 잠기므로 선언 후 대기가 바뀌지 않는다 → "론으로 잡았다"는 곧
> "공개된 오름패를 버렸다"와 같다.

그런데 **연금술사**(48차에 "리치 중 사용 금지" 삭제, 게임당 5회, 수패 숫자 ±1)와
**염색**(48차에 동일 해제, 게임 내 5회, 수패 무늬 변경)은 **리치 중에도 손패를 바꾼다.**

결과: 오픈 리치로 공개한 오름패와 실제 대기가 달라진다. 상대는 **공개되지 않은 패로**
역만(오픈 리치 직격 13판)을 맞는다. 오픈 리치의 하우스룰 근거 자체가 무너진다.

**🟡 판정: 유지** (2026-07-27 사용자 확정). 오픈 리치가 이미 오름패를 공개한 상태이고,
보유 증강도 전원 공개이므로 **상대는 "연금술사로 ±1까지, 염색으로 같은 숫자 다른 무늬까지
바뀔 수 있다"는 범위를 계산할 수 있다.** 완전한 무정보 기습이 아니라 "공개된 대기 + 공개된
변형 범위"를 읽는 문제라, Rule #4(대응 가능성)를 만족한다고 본다.

다만 `open_riichi_reveal.ts`의 주석이 "리치는 손이 잠기므로 대기가 바뀌지 않는다"를
전제로 서술돼 있어, 그 전제가 더 이상 참이 아니라는 사실은 주석에 남겨야 한다(미착수).

## D-2. 거신병 × 리치 — 가드 없음 (코드 확인, 실기 미검증)

`giant_god.ts`의 validate에는 **리치 검사가 없다**(같은 계열인 tile_split·genesis·even_world는
"리치 중 오름패 고정과 충돌"을 이유로 명시적으로 막는다). 조건만 맞으면 리치 중에도
손패 13장을 통째로 국사무쌍으로 갈아치울 수 있다.

같은 이유로 **red_five_touch**(리치 중 손패를 적도라로 만들어 공짜 도라)·
**honor_return**도 리치 가드가 없다. (거신병만큼 파괴적이진 않다.)

이 항목은 액션 validate를 코드로 확인한 결과이고, 리치 상태에서 실제로 발동시켜
정산까지 돌려 보지는 못했다.
