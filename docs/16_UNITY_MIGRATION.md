# 16_UNITY_MIGRATION
Version : 0.1 (초안)
Status : Planning
Last Updated : 2026-07-28

웹(React) 클라이언트 기반 증강마작을 **스팀 출시 가능한 유니티 게임**으로 이행하기 위한
회차별 마이그레이션 계획. 한 회차 = 개발 세션 1회 분량(작게는 반나절, 크게는 1~2일)을
목표로 쪼갠다. 총 8단계 · 45회차.

# 0. 전략 — 무엇을 옮기고 무엇을 유지하는가

## 0.1 핵심 결정: 서버와 엔진은 그대로, 유니티는 "새 클라이언트"

현재 아키텍처(00_MASTER_ARCHITECTURE)의 성질 덕분에 가장 싸고 안전한 경로가 명확하다.

- `@majak/core`(엔진·증강·채점)는 **순수 TypeScript, I/O 없음, 서버에서만 실행**된다.
- 클라이언트는 원래부터 "PlayerView를 그리고 ActionRequest를 보내는" 얇은 층이다.
- 따라서 **증강 시스템을 C#으로 포팅할 필요가 전혀 없다.** 유니티 클라이언트가
  기존 WebSocket JSON 프로토콜(protocol.ts)을 그대로 말하면, 증강 65종+·채점·리플레이·
  봇·통계가 전부 그대로 동작한다.

```
[Unity 클라이언트 (C#)] ──WebSocket JSON──▶ [@majak/server (Node)] ──▶ [@majak/core + content]
[웹 클라이언트 (유지)]  ──────동일 프로토콜────▶        동일 서버
```

새 증강 추가도 지금처럼 content 패키지에 TS 파일 하나 — 클라이언트는 catalog 메시지로
이름·등급·설명을 받으므로 (이미 하드코딩 제거됨) **유니티 재빌드 없이 증강이 늘어난다.**
액티브 증강 버튼처럼 클라이언트가 알아야 하는 목록(ACTIVE_AUGMENT_IDS 등)만
서버 catalog에 필드로 옮겨 데이터 주도로 만든다 (1단계에서 처리).

## 0.2 웹 클라이언트의 역할 변화

웹 클라를 버리지 않는다. 이후 역할:

- **레퍼런스 구현**: 유니티에서 화면이 이상하면 같은 서버에 웹으로 접속해 비교.
- **개발·디버그 도구**: 리플레이 뷰어, 관전, 서버 스모크 테스트.
- **교차 플레이 테스트**: 웹 1명 + 유니티 1명 + 봇 2명으로 프로토콜 호환 검증.

## 0.3 리스크와 미리 정하는 것

| 항목 | 내용 |
|------|------|
| 서버 상시 운영 | 스팀 유저는 불특정 다수 — 현행 macOS 홈서버로는 부족. Linux VPS + TLS(wss) + 프로세스 관리로 이전 (1단계). 턴제라 지연에 관대해 단일 리전으로 시작 가능 |
| 온라인 전용 | 싱글(봇전)도 서버가 필요. MVP는 온라인 전용으로 출시하고, "로컬 Node 서버 동봉 오프라인 봇전"은 출시 후 선택 과제(§9) |
| 프로토콜 동결 | 유니티 개발 중 서버 프로토콜이 흔들리면 양쪽이 같이 깨진다. 1단계에서 `protocolVersion` 핸드셰이크 + 스키마 스냅샷 테스트로 고정 |
| 디자인 미확정 | 전 UI를 **플레이스홀더 스킨 + 교체 슬롯** 구조로 만든다(7단계). 디자이너 산출물은 "스프라이트/폰트/색 토큰을 슬롯에 꽂는" 작업으로 수렴시키는 것이 목표 |
| Steam 로그인 | 기존 id/비번 계정과 별개로 Steam 세션 티켓 인증 경로를 서버에 추가(1단계 설계, 6단계 연결). 웹용 계정 시스템은 공존 |

## 0.4 확정할 기술 스택 (1회차에서 최종 결정)

| 영역 | 제안 | 비고 |
|------|------|------|
| Unity 버전 | Unity 6 LTS (6000.x) | 출시까지 버전 고정 |
| UI | uGUI(Canvas) + TextMeshPro | 디자이너 산출물이 스프라이트일 가능성이 높고 레퍼런스가 많음. UI Toolkit은 차기 검토 |
| WebSocket | System.Net.WebSockets 래핑 (또는 NativeWebSocket) | 스팀 데스크톱 전용이라 WebGL 제약 없음 → 표준 API로 충분 |
| JSON | Newtonsoft Json (com.unity.nuget.newtonsoft-json) | 다형 메시지(type 태그) 처리 용이 |
| Steam SDK | Steamworks.NET | 성숙·문서 풍부. Facepunch.Steamworks 대안 검토 가능 |
| 에셋 교체 | Addressables + ScriptableObject 스킨 | 디자인 교체를 코드 수정 없이 |
| 테스트 | Unity Test Framework (EditMode 위주) | 프로토콜 역직렬화·상태 스토어 검증 |

# 1단계 — 서버 사전 작업 (유니티 시작 전, 5회차)

유니티를 열기 전에 서버 쪽 "계약"을 먼저 굳힌다. 전부 기존 웹 클라와 호환을 유지한다.

### 회차 1. 기술 스택·저장소 구조 확정
- §0.4 스택 최종 결정 기록 (이 문서 갱신).
- 모노레포에 `unity/` 디렉토리 신설 방침: `newMajak/unity/MajakClient/` (Unity 프로젝트).
- Unity용 .gitignore(Library/, Temp/, Logs/, obj/ 등), 대용량 에셋 대비 git-lfs 도입 여부 결정.
- **완료 기준**: 이 문서 §0.4가 "제안"에서 "확정"으로 바뀜.

### 회차 2. 프로토콜 동결 — 버전 핸드셰이크 + 스키마 스냅샷
- `protocol.ts`에 `protocolVersion` 상수 + join/login 계열 메시지에 버전 필드 추가.
  서버는 불일치 시 명시적 에러(`error: protocolMismatch`)로 거부 (구 웹 클라는 무버전 → 허용 유예).
- 전 메시지 타입(클라→서버 ~23종, 서버→클라 ~22종)의 **샘플 JSON fixture 생성 스크립트**
  작성 → `fixtures/protocol/*.json`으로 커밋. 이후 유니티 역직렬화 테스트의 골든 파일이 된다.
- 프로토콜 문서(12_NETWORK_REPLAY) 최신화: 메시지별 필드·발생 시점 표.
- **완료 기준**: fixture 생성이 CI/테스트로 돌고, 서버 테스트에 버전 핸드셰이크 케이스 추가.

### 회차 3. 클라이언트 하드코딩의 서버 이전 (데이터 주도화)
- 웹 클라 `ACTIVE_AUGMENT_IDS` / `AUGMENT_ACTION_TYPES` 등 "클라가 알아야 하는 증강 지식"을
  서버 `catalog` 메시지 필드로 이동 (`isActive`, `actionType`, `activeLabel` 등).
- 컷인·배너 트리거 조건 중 클라 추론에 의존하는 것이 있으면 서버 `actionFx`/이벤트 기반으로 정리.
- 웹 클라도 catalog 기반으로 전환해 동작 동일함을 확인 (웹이 첫 소비자 = 검증기).
- **완료 기준**: 웹 클라에서 증강 관련 하드코딩 목록 제거, 전체 테스트 통과.

### 회차 4. 랜덤 매칭(매치메이킹) 서버 구현
- 프로토콜: `queueJoin` / `queueLeave` (클라→서버), `queueStatus`(대기 인원·경과) /
  `matchFound`(방 배정) (서버→클라).
- RoomManager에 매칭 큐: 4명 모이면 자동 방 생성 → 전원 입장 → **자동 시작**(대기실 생략) 옵션.
- 정책 결정: 대기 N초 초과 시 봇으로 채워 시작할지(권장: 옵션으로 제공), 취소·이탈 처리,
  중복 큐 방지, 매칭 후 미응답자 처리(큐 복귀).
- **완료 기준**: FakeSocket 통합 테스트 — 4명 큐 진입→자동 게임 시작, 2명+타임아웃→봇 2 채움 시작,
  큐 이탈·중복 진입 거부. 웹 클라에 임시 "랜덤 매칭" 버튼으로 실동작 확인.

### 회차 5. Steam 인증 경로 설계·서버 구현 (클라 연결은 6단계)
- 프로토콜: `steamLogin { ticket, steamId, personaName }` → 서버가 Steam Web API
  `ISteamUserAuth/AuthenticateUserTicket`(Publisher Web API Key 필요)로 검증 → 기존 세션 토큰 발급.
- SiteDb에 `steamId` 필드 추가: steamId ↔ 계정 매핑(최초 로그인 시 자동 계정 생성,
  닉네임은 페르소나명 기반 + 중복 시 접미사). 기존 id/비번 계정과 공존.
- 개발용 우회: `STEAM_AUTH_FAKE=1`이면 티켓 검증 생략하고 steamId를 신뢰(로컬 개발 전용, 프로덕션 금지).
- 통계·리플레이·재접속 토큰 등 기존 시스템이 steam 계정에도 그대로 적용되는지 확인.
- **완료 기준**: 서버 테스트 — 가짜 검증기 주입으로 steamLogin 성공/실패/재로그인 케이스.
  (실 티켓 검증은 6단계에서 App ID 발급 후 E2E.)

> 참고: 서버 실배포 현대화(Linux VPS·wss·systemd/도커)는 6단계 전까지만 되면 된다 → 회차 36.

# 2단계 — 유니티 프로젝트 기반 (4회차)

### 회차 6. 프로젝트 생성·규약·씬 골격
- Unity 프로젝트 생성 (`unity/MajakClient`), 2D/URP 여부 결정(UI 중심이므로 Built-in+uGUI로 충분).
- 폴더 규약: `Scripts/{Net,State,UI,Game,Skin,Steam}`, `Prefabs/`, `Skins/Placeholder/`.
- 씬 3개: `Boot`(초기화·연결) → `Lobby`(홈·대기실) → `Game`(대국). 씬 로더/전환 유틸.
- 어셈블리 정의(asmdef) 분리: `Majak.Net`(엔진 비의존) / `Majak.Game` — 테스트 용이성 확보.
- **완료 기준**: 세 씬 전환이 도는 빈 골격 + 첫 커밋(.gitignore 검증).

### 회차 7. 네트워크 레이어 — WebSocket 클라이언트
- `WsClient`: 연결/송신/수신 루프(백그라운드 스레드)→메인스레드 디스패치 큐, 상태
  (Disconnected/Connecting/Connected), ping/pong 유지, 지수 백오프 자동 재연결.
- `MessageRouter`: 수신 JSON의 `type`으로 분기해 타입별 핸들러 등록.
- 재접속 시나리오는 기존 웹 클라와 동일하게: join/reconnect token 저장(PlayerPrefs) → 재연결 시 복원.
- **완료 기준**: EditMode 테스트(가짜 소켓으로 라우팅·재연결 백오프), 로컬 서버에 연결해 pong 수신.

### 회차 8. 프로토콜 DTO (C#) + 골든 파일 역직렬화 테스트
- protocol.ts 전 메시지의 C# 클래스 작성. **회차 2의 fixture JSON을 유니티 테스트 리소스로 복사**해
  전 타입 역직렬화·재직렬화 라운드트립 테스트 (필드 누락·이름 불일치를 여기서 전부 잡는다).
- PlayerView·ZoneView·PromptInfo·MeldInfo 등 뷰 모델 포함 (가장 크고 중요한 부분).
- fixture 갱신 시 자동 복사 스크립트(npm script) — 서버가 바뀌면 유니티 테스트가 빨간불이 되는 구조.
- **완료 기준**: 전 메시지 타입 라운드트립 테스트 통과.
- ※ 수작업이 부담이면 ts→C# 코드젠 검토하되, 메시지 수십 종 규모면 수작업+골든 테스트가 더 단순.

### 회차 9. 클라이언트 상태 스토어
- `ClientState`: 최신 PlayerView, 활성 prompt, draftOffer, catalog(증강 사전), lobby, 세션 정보.
- 변경 알림(C# event) 기반 — UI는 스토어를 구독해 다시 그린다 (React의 state 역할).
- 웹 클라 `detectTransitions`(국 전환·리치·부로 감지 → 연출 트리거)의 논리를 C#로 이식할
  자리(`TransitionDetector`)를 만들어 두되, 연출 소비는 5단계에서.
- **완료 기준**: 녹화된 view 시퀀스(fixture)를 흘려 상태 전이 EditMode 테스트.

# 3단계 — 로비·방 시스템 (5회차)

이 단계부터 매 회차 "실서버 + 유니티 에디터"로 눈 검증한다. UI는 전부 플레이스홀더
(회색 패널 + 시스템 폰트) — 예쁘게 만드는 데 시간 쓰지 않는다.

### 회차 10. 부트·로그인 화면 (개발용)
- Boot 씬: 서버 주소 설정(개발/프로덕션), 연결 → 버전 핸드셰이크 → 로그인 화면.
- 개발 로그인: 기존 register/login/tokenLogin (Steam 연결 전까지의 임시 경로.
  UI를 `IAuthProvider` 뒤에 두어 6단계에서 SteamAuthProvider로 갈아끼우게 설계).
- 자동 로그인(저장된 토큰) + 실패 시 폼 표시.
- **완료 기준**: 유니티에서 실서버 가입·로그인·재시작 후 토큰 자동 로그인.

### 회차 11. 홈(로비) 화면
- 버튼: 방 만들기 / 코드로 입장 / 랜덤 매칭 / (관전·리플레이는 후순위 표시만).
- lobby 메시지 소비: 내 전적 요약, 진행 중 게임 재입장(resume) 안내.
- **완료 기준**: lobby 수신 데이터가 화면에 표시.

### 회차 12. 방 생성·코드 입장
- createRoom → roomCreated(방 코드 표시·클립보드 복사), joinRoom(코드 입력·에러 처리
  — 없는 방/꽉 참/진행 중).
- **완료 기준**: 유니티 2인(에디터+빌드)로 코드 입장 상호 확인. 웹 클라와 교차 입장도 확인.

### 회차 13. 대기실
- 좌석 4칸: 닉네임, 방장 왕관, 준비 배지, BOT 표시, 상대 누적 전적 칩(stats).
- 조작: 준비 토글, 방장 전용 — 봇 추가/제거·게임 시작(canStart 조건 표시), 나가기.
- 게임 시작 수신 → Game 씬 전환.
- **완료 기준**: 유니티 방장 + 웹 1명 + 봇 2 구성으로 시작까지 진행 (씬 전환 후는 아직 빈 화면).

### 회차 14. 랜덤 매칭 클라이언트
- 큐 진입/취소 UI, queueStatus(대기 인원·경과 표시), matchFound → 자동 입장·시작 흐름.
- **완료 기준**: 유니티 2 + 웹 2로 4인 매칭 성립. 타임아웃 봇 채움 옵션 동작.

# 4단계 — 인게임: 플레이 가능한 최소 대국 (11회차)

웹 App.tsx(~3,300줄)가 하던 일을 유니티로 옮기는 본체. 순서는 "봇 3과 한 국을 눈으로
완주"를 최단으로 뚫은 뒤 살을 붙인다. 모든 시각 요소는 플레이스홀더 스킨(§7) 슬롯을 통해 그린다.

### 회차 15. 테이블 레이아웃 + 타일 렌더 기초
- Game 씬: 4방향 좌석 컨테이너(하=나, 우/상/좌=상대, 시점 회전), 중앙 정보 패널
  (장풍·국·본장·공탁·남은 패산·도라 표시패), 점수·풍 표시.
- `TileView` 프리팹: 스프라이트 슬롯 + 뒷면 + 적도라 + 커스텀 suit 텍스트 폴백 +
  conjured 이펙트 자리. 오브젝트 풀. 임시 스프라이트는 웹의 `public/tiles/` 37장 재사용.
- **완료 기준**: 관전 또는 봇전 view를 받아 중앙 정보·점수가 갱신됨.

### 회차 16. 손패 렌더·기본 버림
- 내 손패 13(+쯔모 1 분리) 표시, kind 정렬(자동정렬 설정은 후순위), 상대 손패 뒷면 장수.
- discard prompt에서 패 클릭 → action 전송. 턴 하이라이트·남은 시간 표시.
- **완료 기준**: **유니티로 봇 3과 배패→쯔모→버림 루프가 돈다.**
- ※ true_dragon(17장) 같은 가변 손패 수를 레이아웃이 수용하는지 이 회차에서 확인.

### 회차 17. 버림 강·부로·리치 표시
- 버림 강 6열 배치, 리치 선언패 90도 회전, 부로로 가져간 패 표시 처리.
- 멜드 존: 펑/치/깡(안깡 뒷면 2장)·kokushi_pon 등 `MeldInfo.kind` 데이터 주도 렌더.
- **완료 기준**: 웹 클라와 같은 국을 관전으로 나란히 띄워 렌더 일치 확인.

### 회차 18. 리액션·턴 프롬프트 전체
- 턴 옵션: 리치(가능 패 하이라이트)·쯔모·안깡/가깡 후보·증강 액션 등 prompt 옵션을
  **데이터 주도 버튼 목록**으로 (하드코딩 최소화 — 서버가 주는 옵션을 그대로 나열).
- 리액션: 론/펑/치(조합 선택)/대명깡/커스텀 콜 + 스킵. 타임아웃 기본 행동 표시.
- **완료 기준**: 봇전에서 펑·치·깡·리치·론·쯔모 전부 유니티 입력으로 성사.

### 회차 19. 리치·후리텐 보조 표시
- 리치 후 잠긴 패 딤 처리 + 쯔모기리 자동 진행, 대기패 미리보기(hover), 후리텐 표시.
- **완료 기준**: 리치 상태 UX가 웹과 동등.

### 회차 20. 증강 드래프트 UI
- draftOffer 수신 → 3지선다 카드 패널(등급 색·이름·설명·⚡액티브 뱃지), 선택 → draftPick.
- 타 플레이어 픽 공개 표시(전원 공개 원칙), 대기 중 상태.
- **완료 기준**: 게임 시작·남장 드래프트 2회를 유니티로 완주.

### 회차 21. 증강 패널·액티브 발동·augmentView
- 내/상대 보유 증강 상시 표시 + 툴팁. 액티브 증강 발동 버튼(복수 보유 시 선택 메뉴).
- `augmentView` 채널 소비: 투시·간파·봉인 목록 등 증강 전용 정보 표시(범용 리스트/패 표시로).
- **완료 기준**: 액티브 증강(회수·절벽 위 꽃 등) 실발동, 투시류 정보 표시 확인.

### 회차 22. 국 결과 화면
- roundOver: 화료자·역 목록·부판·점수 이동·우라 공개·유국(텐파이/노텐)·특수 유국 표시.
- 닫기(자동 5초/수동) → roundContinue ack 전송 (전원 닫으면 다음 국 — 기존 게이트 그대로).
- **완료 기준**: 반장전 전 국의 결과 화면이 정상 표출·진행.

### 회차 23. 게임 종료·통계·무효 투표
- gameOver: 최종 순위·우마·오카 정산 표. 통계 탭(이번 판/누적). 홈 복귀.
- abortVote 배너(동의/반대), gameAborted 처리. 도중 퇴장·포기 UX.
- **완료 기준**: **유니티 단독으로 반장전 완주 + 통계 확인 — "플레이 가능한 게임" 마일스톤.**

### 회차 24. 재접속·복원 하드닝
- 대국 중 강제 종료→재실행→토큰 재입장→view 복원. 프롬프트 중·드래프트 중·결과 화면 중
  재접속 매트릭스 점검. 관전 진입/이탈.
- **완료 기준**: 재접속 매트릭스 표 전 항목 통과.

### 회차 25. 인게임 마감 스윕
- 4단계에서 미룬 자잘한 것 일괄: 남은 표시 누락(본장·공탁 세부), 에러 토스트, 프롬프트
  타임아웃 시각화, 무효 투표 접근 위치 등. 웹 클라와 기능 비교 체크리스트 작성·소거.
- **완료 기준**: "웹에는 있는데 유니티에 없는 인게임 기능" 목록이 연출(5단계) 항목만 남음.

# 5단계 — 연출·QoL (4회차)

### 회차 26. 연출 큐 + 배너
- 웹의 productionQueue(순차 재생 큐, 결과창 드레인 게이트)를 C#로 이식.
- 국 시작 배너, 리치·부로 배너, 멱등 처리(재접속 시 헛알림 금지 — bannerShown 로직 이식).
- **완료 기준**: 알림 폭주 상황(론+새 국)에서 순서 보장: 리치→론→점수표→다음 국.

### 회차 27. 컷인·사운드
- 론/쯔모 컷인, 만관~삼배만 등급별 연출, 역만 전용 연출 — 전부 플레이스홀더 비주얼로
  타이밍만 완성 (그래픽은 디자이너 산출물로 교체될 슬롯).
- 사운드 훅(`SfxPlayer`): 웹 sfx.ts의 트리거 지점 대응표 작성, 임시 사운드 연결.
- **완료 기준**: 트리거 타이밍이 웹과 동등.

### 회차 28. 설정·손패 조작 QoL
- 설정 패널: 자동정렬·자동화료·후로없음·사운드 볼륨 (PlayerPrefs 저장).
- 손패 드래그 수동 정렬(자동정렬 OFF 시), 드래그 고스트·삽입 위치 처리.
- **완료 기준**: 설정이 대국 중 즉시 반영·재시작 후 유지.

### 회차 29. 접속 상태·전환 연출
- 연결 끊김 오버레이·재연결 진행 표시, 씬 전환 로딩, 상대 이탈/복귀 표시.
- **완료 기준**: 서버 재시작·네트워크 차단 시나리오에서 UX가 명확.

# 6단계 — 스팀 통합 (5회차)

### 회차 30. Steamworks 준비
- 스팀 파트너 등록·앱 크레딧 구매 → **App ID 발급** (외부 절차 — 리드타임이 있으니
  이 단계 전에 미리 신청 권장). Publisher Web API Key 발급(서버 티켓 검증용).
- Steamworks.NET 도입, `SteamManager` 수명주기(초기화 실패 시 안내 후 종료), steam_appid.txt 개발 환경.
- **완료 기준**: 에디터·빌드에서 SteamAPI 초기화 + 페르소나명 로그 출력.

### 회차 31. Steam 로그인 연결
- `SteamAuthProvider`: GetAuthSessionTicket → 회차 5의 `steamLogin` → 세션 수립.
  티켓 만료·재발급, 로그인 실패 폴백 UX.
- 개발 로그인 폼은 개발 빌드 전용으로 격리 (프로덕션 빌드에서 비노출).
- **완료 기준**: 실 스팀 계정으로 서버 로그인 E2E, 통계가 steam 계정에 누적.

### 회차 32. 초대·리치 프레즌스
- Rich Presence("동3국 플레이 중" 등), 친구 목록 초대: 초대 수락 시 방 코드로 joinRoom
  (커맨드라인/`connect` 스트링 → 부트 시 파싱). 오버레이 동작 확인(오버레이는 렌더 훅이라
  Built-in 파이프라인에서 보통 무설정).
- **완료 기준**: 친구 초대 → 자동 방 입장 E2E.

### 회차 33. 빌드 파이프라인
- Windows 64bit 우선(+ macOS는 여력 시), 빌드 스크립트(버전 스탬프, 개발/프로덕션 서버 주소 분리).
- steamcmd 업로드 스크립트(depot/branch 구성, beta 브랜치 운영), 빌드→업로드 원커맨드화.
- **완료 기준**: 스팀 클라이언트에서 beta 브랜치로 설치·실행·접속.

### 회차 34. 스팀 환경 하드닝
- 오버레이 중 입력 처리, 창 모드/해상도 옵션, 종료 시 세션 정리(방 이탈 처리),
  스팀 오프라인 모드 시 안내, 중복 실행 방지.
- **완료 기준**: 스팀 배포 빌드로 반장전 완주(교차: 스팀 2 + 웹 1 + 봇 1).

> 서버 실배포(회차 36)가 이 단계 완료 전 필요 — 실 스팀 테스트는 wss 공개 서버가 있어야 원활.

# 7단계 — 디자인 적용 준비 (스킨 시스템, 4회차)

디자이너 산출물이 도착했을 때 **코드 수정 없이 꽂는** 구조. 4~5단계에서 이미 슬롯을
쓰도록 만들었으므로 여기서는 체계화·문서화가 중심.

### 회차 35. TileSkin·UI 테마 자산화
- `TileSkin`(ScriptableObject): 표준 34종+적도라 3 스프라이트 슬롯, 뒷면, 커스텀 suit 폴백
  규칙, conjured 이펙트 파라미터. 런타임 스킨 교체 테스트(설정에서 스킨 전환).
- `UiTheme`(ScriptableObject): 색 토큰(등급 Silver/Gold/Prism 색 포함), 폰트(TMP 에셋),
  공통 스타일. 하드코딩 색·폰트를 전수 조사해 토큰 참조로 치환.
- **완료 기준**: 더미 제2스킨으로 전 화면 전환 시 코드 수정 0.

### 회차 36. 서버 실배포 현대화 (병행 회차)
- Linux VPS(+도커 또는 systemd), TLS(wss) 리버스 프록시, 도메인, 헬스체크·재시작 정책,
  리플레이·stats 볼륨 백업. 개발(맥)/프로덕션 서버 주소를 클라 설정으로 분리.
- **완료 기준**: 유니티·웹 모두 wss 공개 서버로 정상 플레이, 서버 프로세스 재시작 후 재접속 복원.

### 회차 37. 레이아웃 파라미터화·해상도 대응
- 좌석·강·손패 배치 수치를 인스펙터/에셋 데이터로 노출 (디자이너 배치 결정을 수치로 반영
  가능하게). 기준 해상도 1920×1080, 16:10·21:9 안전영역, 최소 지원 해상도 결정, UI 스케일 정책.
- **완료 기준**: 해상도 3종에서 깨짐 없음.

### 회차 38. 디자이너 핸드오프 문서
- 필요한 에셋 전량 목록: 타일 37종(권장 해상도·여백·네이밍 규칙), 탁자/배경, UI 아틀라스,
  컷인/배너 이미지, 폰트, 사운드 목록. 임포트 절차(폴더에 넣고 SO에 연결)와 미리보기 씬 제공.
- 컨셉 확정 시 영향 범위 표(무엇이 교체 가능하고 무엇이 코드 작업인지).
- **완료 기준**: 문서를 보고 제3자가 스킨을 갈아끼울 수 있는 수준.

# 8단계 — 안정화·출시 (7회차)

### 회차 39. 부하·수명 테스트
- 서버: 동시 방 N개(봇 게임 대량 구동) 부하, 메모리·이벤트 로그 크기 관찰, 장시간 구동.
- 클라: 반장전 연속 플레이 시 GC 할당·드로우콜 프로파일, 타일 풀 검증, 메모리 누수(씬 왕복).
- **완료 기준**: 목표 수치(예: 동시 20방·클라 60fps 유지) 정의·달성.

### 회차 40. 크래시·오류 계측
- 클라 로그 수집(로컬 파일 + 옵트인 업로드), 서버 구조화 로그·에러 알림.
  프로토콜 에러/역직렬화 실패의 안전 처리(게임이 죽지 않고 재동기화).
- **완료 기준**: 의도적 오류 주입 시 복구 또는 명확한 안내.

### 회차 41. 클로즈드 플레이테스트 (Steam Playtest)
- Playtest 앱 설정 또는 베타 키 배포. 피드백 폼·리플레이 자동 수집으로 밸런스 데이터 확보.
- **완료 기준**: 외부 인원 N명 이상 실플레이 데이터 수집.

### 회차 42~43. 피드백 반영 (2회차 예약)
- 플레이테스트에서 나온 UX·밸런스·버그 수정. (증강 밸런스는 서버 콘텐츠 수정만으로 배포
  없이 반영되는 것이 이 아키텍처의 이점 — 확인 겸 활용.)

### 회차 44. 상점 페이지·출시 준비
- 상점 페이지(스크린샷·트레일러·설명 — 디자인 확정 후), 심의 필요 여부 확인(한국 GRAC 등
  지역 정책), 가격·출시일, 리뷰 빌드 제출(Steam 빌드 리뷰 리드타임 고려).
