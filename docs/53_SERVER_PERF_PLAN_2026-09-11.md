# 서버 성능 계획 (2026-09-11)

목표: 맥미니 한 대에서 **동시 테이블 수를 늘려도** 응답이 늘어지지 않게 하고, 나중에
클라우드(다중 인스턴스)로 옮길 때 다시 뜯지 않아도 되는 구조로 정리한다.

## 0. 실측 — 무엇이 무거운가

측정: `npm run arena -- --games 6 --augments` 를 `node --cpu-prof` 로 돌렸다
(봇 4명, 생각 시간 0, 네트워크 없음 = 판 하나의 **순수 CPU 원가**).

- 반장 1판 ≈ **4~5초 CPU** (증강 유무 차이 거의 없음). 결정 한 번(턴 프롬프트 + 봇 판단 +
  뷰 4장 방송) ≈ **8 ms**, 이 동안 이벤트 루프가 막힌다.
- 시간이 어디로 가는가 (inclusive):

  | 비율 | 어디 | 왜 |
  |---|---|---|
  | **58%** | `winningKinds` (34종 × `isWinningShape`) | 아래 세 호출처가 전부 이걸 탄다 |
  | 43% | `turnPrompt` → 손패 14장마다 `validate("riichi")` | 리치 가능 여부를 **버릴 패마다** 34종 화형 판정으로 확인 = 턴마다 ~476회 |
  | 14% | `buildPlayerView` (후리텐 계산 포함) | 이벤트마다 4명 뷰 재생성, 안에서 또 `winningKinds` |
  | 23% | `BotAgent.decideNow` (샹텐·우케이레·위험도) | 봇 본체 — **의외로 작다** |
  | 13% (self) | `shapeMemoKey` | 메모 **키 문자열 만들기**(map·sort·join)가 판정 자체와 맞먹는다 |
  | 7% | GC | 위 문자열·배열 쓰레기 |
  | ~3% | `__name`/TextDecoder | `tsx` 온더플라이 변환의 흔적 — 운영도 `tsx`로 돈다 |

결론: **"봇이 무겁다"가 아니라 "코어 엔진의 화형 판정이 무겁고, 봇 3명은 그걸 3배로
부른다"** 이다. 사람 4명 테이블도 같은 원가를 낸다(봇은 생각 지연으로 분산될 뿐).

수용량 어림: 테이블 하나가 초당 1~2 결정 → 8~16 ms/s. 단일 스레드라 **테이블 60~100개
근처에서 한 코어가 찬다.** 그 전에 이미 버스트(리액션 경합에 봇 셋이 동시에 계산)로
체감 지연이 온다. 맥미니는 코어 8개인데 1개만 쓴다.

## 1단계 — 엔진 원가 3~5배 절감 (코어, 위험 낮음, 효과 큼)

전부 `packages/core`이고 결정론이 바뀌지 않으므로 기존 테스트가 곧 회귀 방어선이다.
각 항목은 아레나 시간(`--games 20`, 기준 **83 s**)으로 전후를 잰다.

1. **`shapeMemoKey` 를 싸게** — kind를 34칸 정수 카운트 배열로 접어 키를 만들고,
   `NormalizedOptions` 는 `normalizeOptions` 에서 한 번 계산한 `optsKey` 문자열을 붙여 둔다.
   (map/sort/join 제거. 예상: 전체의 10%+.)
2. **리치 검증의 34종 판정을 텐파이 사전검사로 자른다** — `turnPrompt`는 14장을 도는데
   14장 손이 텐파이가 될 수 있는 버림은 보통 0~2개다. 손 전체(14장)의 화형·샹텐을
   **한 번** 보고 안 되면 14회 전부 건너뛴다. 옵션(조커·혼합 몸통 등)이 있는 손은
   기존 경로로 떨어뜨려 정확성을 지킨다. (예상: 전체의 30%+.)
3. **`winningKinds` 의 상태별 메모를 `turnPrompt` 에도** — `helpers.ts`의
   `WAITS_CACHE`/`memoOn`(state 단위 무효화)을 `standardActions`의 리치 검증과
   `FlowController.reactionPrompts` 의 후리텐 계산이 같이 쓰게 한다. 한 턴 안에서 같은
   손을 여러 번 묻는 일이 없어진다.
4. **뷰 방송을 델타가 아니라 "바뀐 사람만"** — `broadcastViews` 11곳 중 실제로 넷 다
   바뀌는 이벤트는 절반이 안 된다. 후리텐 사유 계산은 손이 바뀐 사람만 다시 한다.
   (보수적으로: 뷰 자체는 그대로 만들고 `buildFuritenReasons` 만 메모.)
5. **운영 실행을 `tsx` 대신 빌드된 JS로** — `esbuild` 번들(`keepNames` 없이) 또는
   `tsc` 출력으로 `deploy/serve.sh` 가 띄운다. 기동도 빨라진다. `--cpu-prof` 결과가
   깨끗해지는 부수 효과.

완료 기준: 아레나 20판 **≤ 25 s**, `npm test` 전부 통과, 리플레이 재현 테스트 동일.

## 2단계 — 봇을 이벤트 루프에서 떼기 (서버, 위험 중간)

1단계 뒤에도 봇 결정은 그 순간 루프를 막는다. 봇 셋이 동시에 리액션을 재면 사람 응답이
그만큼 밀린다.

- **결정 예산 분산**: 이미 있는 `think()` 지연 안에서 무거운 계산(`buildRead`)을
  `setImmediate` 로 한 번 양보한 뒤 돌린다 — 값싼 완화, 먼저 한다.
- **worker_threads 봇 풀**: `BotAgent.decideNow` 는 순수 함수(`PlayerView` + 프롬프트 →
  액션)라 워커로 보내기 좋다. 워커 N개(코어-2)에 라운드로빈, 메시지는
  `structuredClone` 비용이 있으니 뷰 크기를 먼저 잰다. 결정론(시드 PRNG)은 봇 상태를
  워커에 두고 방 코드로 고정한다. 아레나에 `--workers` 스위치를 붙여 같은 시드로
  결과가 동일한지 검증한다.

## 3단계 — 테이블 단위 격리 (클라우드 준비, 위험 높음, 별도 브랜치)

클라우드로 갈 때 필요한 것은 "서버를 여러 개 띄워도 한 테이블은 한 프로세스에 있다"는
구조다. 지금 `RoomManager`(7,100줄)가 접속·인증·로비·친구·관리자·게임 진행을 한
객체에서 다루고, `SiteDb`(node:sqlite, **동기**)를 같은 스레드에서 친다.

- **분리 순서**: (a) 게임 진행(`openGame`~`resetRoomAfterGame`·리플레이·통계 기록)을
  `TableRunner` 로 떼어 RoomManager 는 메시지 라우팅만 → (b) `TableRunner` 를
  worker/프로세스로 옮길 수 있는 경계 확인 → (c) 인증·친구·리더보드 등 사이트 기능은
  그대로 메인에.
- **DB 동기 호출**: 게임 중 호출되는 것(`recordGame`, 라이브 게임 기억, 통계)만 큐로
  모아 국 사이에 쓴다. 클라우드에서는 SQLite → Postgres 교체 지점이 이 큐 하나가 된다.
- **세션 상태 외부화**: 재접속·이어하기가 프로세스 메모리에 의존하는 부분
  (`rememberLiveGame`) 목록을 만들고, Redis 같은 외부 저장으로 옮길 수 있게 인터페이스로 감싼다.

이 단계는 실제 부하가 1단계 완료 뒤에도 문제가 될 때만 한다.

## 4단계 — 관측

지금은 부하가 어느 정도인지 **볼 수 있는 곳이 없다.** `/healthz` 에 다음을 붙인다:
이벤트 루프 지연(p50/p99, `perf_hooks.monitorEventLoopDelay`), 활성 테이블·봇 수,
결정당 ms 히스토그램, 힙. 감시자 로그(`.majak/watchdog.log`)에 1분마다 한 줄. 이게
있어야 "봇 많이 넣으면 무겁다"가 수치가 된다. **1단계와 같이 넣는다** — 전후 비교용.

## 순서와 규모

| 단계 | 규모 | 기대 |
|---|---|---|
| 4 (관측) + 1 (엔진) | 1 PR씩, 며칠 | 원가 3~5배↓, 수용 테이블 수 같은 배수↑ |
| 2 (봇 워커) | 1~2 PR | 봇 버스트가 사람 지연에 안 보임, 코어 여러 개 사용 |
| 3 (테이블 격리) | 긴 브랜치 | 클라우드 다중 인스턴스 가능 |

측정 명령(기준선): `cd packages/server && time node --import tsx/esm src/arenaCli.ts --games 20 --augments`
