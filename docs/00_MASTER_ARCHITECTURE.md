# 3. 패키지 구조 (모노레포)

npm workspaces 기반 모노레포.

```
newMajak/
├── PROJECT_CHARTER.md
├── PROJECT_STATUS.md
├── docs/                  # 00~13, 99 설계 문서
├── packages/
│   ├── core/              # @majak/core    — 순수 게임 엔진 (I/O 없음)
│   ├── content/           # @majak/content — 증강·역 등 콘텐츠 정의
│   ├── server/            # @majak/server  — 권위 서버 (WebSocket, 방, 봇 구동)
│   └── client/            # @majak/client  — React UI
└── replays/               # 게임별 JSONL 이벤트 로그 (서버가 기록)
```

## 의존 방향 (절대 규칙)

```
client ──▶ core ◀── server
             ▲
          content
```

- **core는 아무것도 의존하지 않는다.** Node API, DOM, 네트워크, 파일시스템 금지.
  순수 함수와 데이터만 존재한다. 그래서 서버(권위 실행)와 클라이언트(표시·검증)가 같은 코드를 쓴다.
- **content는 core의 등록 API만 사용한다.** 증강 하나 = content 안의 파일 하나.
  엔진(core)을 수정하는 순간 설계 실패로 간주한다.
- **server와 client는 서로를 모른다.** 공유가 필요한 타입(프로토콜 메시지 등)은 core에 둔다.

# 4. 핵심 데이터 흐름

차터가 확정한 `Action → Event → Effect → GameState` 파이프라인의 전체 그림.

```
 [클라이언트 / 봇]
      │  ① ActionRequest ("나 이 패 버릴래")
      ▼
 [Action System]  ── ② RuleRegistry에 질의: 이 행동이 지금 합법인가?
      │              (불법이면 거부 응답, 상태 변화 없음)
      ▼
 [Event 생성]     ── ③ 합법이면 Action을 Event(들)로 변환 (TileDiscarded 등)
      ▼
 [Effect System]  ── ④ 이 Event에 반응하도록 등록된 Effect들이
      │              우선순위 순으로 실행 (증강의 훅이 여기 걸림)
      │              Effect는 Event를 수정·취소하거나 새 Event를 방출할 수 있다
      ▼
 [Reducer]        ── ⑤ 확정된 Event가 GameState를 갱신 (유일한 상태 변경 지점)
      ▼
 [Event Log]      ── ⑥ 확정 Event를 순서대로 기록 (= 리플레이 = 디버깅 자료)
      ▼
 [Information Layer] ─ ⑦ 플레이어별로 볼 수 있는 것만 걸러낸 PlayerView 생성
      ▼
 [각 클라이언트 / 봇에게 전송]
```

## 불변 규칙

1. **GameState를 바꾸는 유일한 방법은 확정된 Event다.** (Single Source of Truth)
2. **모든 난수는 GameState 안의 시드 PRNG에서 나온다.** `Math.random()`, `Date.now()` 는 core에서 금지.
   → 시드 + Event Log만 있으면 어떤 게임도 완전히 재현된다 (리플레이·버그 재현·디버깅).
3. **서버만 이 파이프라인을 실행한다.** 클라이언트는 ActionRequest를 보내고 PlayerView를 받을 뿐이다. (Server Authority)

## 5.1 Rule System — 증강 충돌의 해답 (Issue 001 해결)

모든 규칙은 `RuleRegistry`에 **이름 붙은 값**으로 존재한다.

```
"riichi.cost"            → 1000
"hand.maxSize"           → 13
"call.pon.enabled"       → true
"yaku.kokushi.allowOpen" → false
```

증강은 규칙을 직접 바꾸지 않고 **Modifier(수정자)를 등록**한다.
같은 규칙에 여러 Modifier가 붙으면 아래 순서로 결정적으로 합성된다.

```
정렬 기준: (Layer, priority, 등록 순서)

Layer:  Base(0) < Silver(100) < Gold(200) < Prism(300) < System(1000)
```

- 등급이 높은 증강이 나중에 적용된다 (= 최종 발언권).
- 같은 등급끼리는 **획득한 순서**대로 적용된다. 항상 결정적이고, 리플레이가 보장된다.
- System 레이어는 엔진 보호용 (예: 점수 하한선 같은 안전장치).

## 5.2 Zone — "패가 있는 공간"의 일반화

패산, 손패, 버림패, 후로, 왕패를 전부 **Zone**이라는 동일한 개념으로 다룬다.

```
wall / deadWall / hand[p] / melds[p] / discards[p] / (증강이 만든 커스텀 Zone)
```

- 모든 패 이동은 "Zone A → Zone B" 연산(TileOperation Event)이다.
- 쯔모 = wall→hand, 버림 = hand→discards, 펑 = discards→melds. 전부 같은 연산의 조합.
- **Prism 증강이 "새로운 Zone 생성"·"벽 구조 변경"을 하려면 Zone을 하나 등록하고
  이동 규칙만 정의하면 된다.** 엔진은 Zone이 몇 개인지 모른다.

## 5.3 Information Layer — 가시성도 규칙이다

서버는 전체 상태를 알고, 각 플레이어에게는 **걸러낸 PlayerView**만 보낸다.

- 각 Zone에는 가시성 Rule이 있다: `visibility.hand[p]` → "본인만", `visibility.discards` → "전원".
- "상대 패 확인", "패산 공개" 같은 Gold/Silver 증강은 **가시성 Rule에 Modifier를 붙이는 것**뿐이다.
- 클라이언트에 전송되지 않은 정보는 해킹으로도 볼 수 없다 (Server Authority의 실질적 의미).

## 5.4 Player Agent — 사람과 봇은 같은 인터페이스

```ts
interface PlayerAgent {
  onView(view: PlayerView): void;                    // 상태 갱신 수신
  decide(prompt: DecisionPrompt): Promise<Decision>; // 선택 요청 (버릴 패, 펑 여부, 드래프트 픽…)
}
```

- 사람 = WebSocket 세션에 연결된 HumanAgent (시간 초과 시 기본 행동).
- 봇 = 같은 인터페이스를 구현한 BotAgent. 모든 후보 행동이 **점수(EV)로 입찰**하고 이긴
  것이 실행된다 — 고정된 우선순위 사슬이 아니다(아래 "입찰 코어").
  액티브 증강 발동은 각 증강 파일의 `AugmentDef.bot` 정책에 위임한다 (10 §6, 콜로케이트).
- 엔진은 상대가 사람인지 봇인지 **모른다.** 혼자서 봇 3명과 테스트 플레이 가능.

**봇의 판단 구조** — `packages/server/src/bot/`. 매 결정마다 뷰 하나로 판을 한 번
읽고(`read.ts`), 여러 평가자가 그 읽기를 나눠 쓴 뒤 전부 같은 축에서 입찰한다.

| 모듈 | 판단 | 근거 |
|------|------|------|
| `decide.ts` | **결정 코어** | 모든 후보가 점수로 입찰하고 이긴 것이 실행된다 (아래 참고) |
| `read.ts` | 판 읽기 스냅샷 | 샹텐·대기·도라·잔여 장수·상대 위협·순위를 결정당 1회 계산 |
| `value.ts` | 값어치 · 화료 확률 | 예상 판수 → 코어 점수표로 **점수**, 대기·우케이레·순목 → 화료 확률. 열린 손은 남의 버림패로도 전진하는 몫까지 센다 |
| `match.ts` | 순위·판돈 | 점수판과 남은 국 수 → 위험 감수 성향 `riskAppetite`(-1 지킨다 ~ +1 뒤집는다) |
| `discard.ts` | 버림 · 리치 | **기대 획득(확률×값어치) − 기대 실점(확률×실점)** 의 뺄셈 하나 |
| `call.ts` | 후로 | 샹텐이 실제로 줄고(역패 펑만 예외) 화료할 역이 있을 때만. 종반엔 형식텐파이 |
| `kan.ts` | 깡 | 손이 상하지 않을 때만. 남이 리치 중이면 새 도라를 열어 주지 않는다 |
| `danger.ts` | 위험 읽기 | 현물·통과패·스지·벽 → 방총 확률, 상대 후로·리치·도라 → **예상 실점**. 곱해서 기대 실점 |
| `suji.ts` | **스지(筋)** | 이 패를 잡는 대기형(량면·간짱·변짱·샤보·단기)을 세워 놓고 스지·벽·장수 셈으로 지워진 몫만 뺀다 |
| `opponents.ts` | 상대 성향 | 뷰 변화만 보고 국을 넘어 리치·후로 비율을 쌓는다 (사전값에 섞어 서서히) |
| `draft.ts` | 증강 픽 | 파워 × **성격 궁합** × 모으던 계열과의 시너지 (계열로 정의해 새 증강도 자동 분류) |
| `arena.ts` | **측정** | 봇끼리 판을 돌려 집계. 2:2 정책 대전으로 **강함**도 잰다 (`npm run arena`) |
| `yaku.ts` | 역 읽기 | 손을 직접 보고 청일색·치또이·일통·산색·찬타·토이토이·산안커·삼색동각·탕야오까지 판수를 잡는다. **역 이름과 판수 표를 봇 전체가 여기 하나로 공유한다** |
| `callAudit.ts` | **콜 기회 집계** | 콜 기회가 어느 관문에서 걸렸는지 센다 (`npm run arena -- --calls`) |
| `openTally.ts` | **후로 국 성적** | 울고 난 국과 안 운 국의 화료율·방총률·타점을 갈라 센다 (`--calls`) |
| `flags.ts` | 실험 스위치 | 새 판단을 스위치 뒤에 두고 2:2로 붙여 본 뒤 채택한다 (임시 비계) |
| `profile.ts` | 성격 | 시드에서 **원형** 하나를 뽑는다 — 공격·수비·속공·타점·균형·변덕 (아래 참고) |

샹텐·우케이레 계산기는 코어(`mahjong/scoring/shanten.ts`)에 있다 — 봇과 증강 정책이 함께 쓴다.

**단일 눈금 (2026-08-05).** 예전에는 판단마다 단위 없는 점수를 손으로 맞췄고
(`push*efficiency + fold*safety*14`), 그래서 서로 다른 판단을 비교할 수 없었다.
지금은 모든 판단이 **점수**라는 눈금 하나 위에서 이루어진다 — 값어치는 코어 점수표
(`calculateScore`)로, 확률은 대기 장수·남은 순목으로 낸다. 성격과 순위 압박은 판단
규칙을 갈라 놓지 않고 이 뺄셈의 양쪽에 곱해지는 **저울**로만 붙는다. 새 판단(증강·깡·
후로)을 이 축에 얹을 때 새 상수를 만들 필요가 없고, 봇이 왜 그렇게 뒀는지도 점수로
설명된다.

게임 모드(반장전/동풍전)는 뷰에 없어 서버가 게임 시작 시 `BotAgent.setGameMode`로
알려 준다 — "지금이 올라스인가"를 알아야 순위를 지키거나 뒤집는 판단이 나온다.

**상대 읽기 (2026-08-05).** 예전 봇에게 상대 셋은 매 국 처음 보는 사람이었다 —
다섯 국 내내 한 번도 안 운 사람과 매 국 세 번씩 우는 사람이 같은 값이었다. 지금은
`opponents.ts`가 **뷰의 변화만 보고**(엔진 무개입, 정보 비대칭 유지) 국을 넘어 성향을
쌓고, 표본이 적을 때는 사전값에 머문다. 그래서 같은 후로·같은 리치라도 **누가 했느냐**로
위협이 갈린다. 판 안에서도 세 신호를 읽는다 — 남의 리치에 현물만 골라 내는 **접은
사람**은 위협에서 빠지고(예전에는 끝까지 무서워했다), **이른 리치**는 비싸게 잡히며,
**한 색만 통째로 안 버리는 사람**은 그 색을 모으는 중으로 본다.

**수비는 대기형을 세워 지운다 (2026-08-06).** 예전 `danger.ts`는 스지와 노찬스를
위험도에 곱하는 상수 두 개로 갖고 있었다(스지 ×0.4, 노찬스 ×0.35). 그러면 **같은
것을 두 번 지운다** — 스지가 지우는 것도 량면이고 벽이 지우는 것도 량면인데 둘이
곱해져 0.14까지 떨어졌다. 그리고 **남는 것이 안 보였다** — 스지는 량면만 지우고
샤보·간짱·변짱·단기는 그대로 남는데, 상수 곱셈에는 그 몫이 어디에도 없었다.

지금은 `suji.ts`가 이 패를 잡는 **대기형을 종류별로 세워 놓고 지워진 것만 뺀다.**
스지는 량면 자리 하나를, 벽은 량면·간짱을, 장수 셈은 샤보·단기를 지운다(샤보는 상대
손에 2장이 있어야 하고 단기는 1장이면 된다 — 사람이 자패 3장을 보고 안전패로 쓰는
셈이 그것이다). 남은 몫이 곧 위험이라 **어떤 패도 0이 되지 않는다** — "스지 하나 보고
안전하다고 하지 말라"가 규칙이 아니라 계산의 성질이 된다.

    무스지 5  6.4%    한스지 5  4.5%    양스지 5  2.6%
    무스지 1  3.3%    스지 1    1.8%    (실측 방총률과 같은 자리에 온다)

여기에 셋이 붙는다. **통과패** — 리치 이후 남이 버렸는데 론하지 않은 패는 현물과
같은 값의 안전패다(예전에는 리치자 본인의 바닥만 셌고, 그래서 안전패가 널린 판에서도
접을 패가 없다고 판단해 무스지를 흘렸다). **신뢰도** — 종반일수록 량면 비율이 낮아
스지가 지울 것 자체가 적고, 리치자는 손이 고정돼 있어 무리치 상대보다 더 믿을 수 있다.
**도라 근처** — 스지라도 도라와 그 옆자리는 위험을 되올린다(깎은 뒤에 곱한다).

900배패 2:2 대전(`--ab noSuji`, 18570국) 결과는 **중립**이다 — 순위 차 +0.0217 ±
0.0265로 스지를 끈 쪽이 근소 우세지만 표준오차 안이고, 240배패에서는 부호가 반대로
나왔다(같은 시드라 240은 900의 앞부분이므로 900이 이를 대체한다). 방총율은 기대한
방향으로 움직인다(스지 쪽 11.4% vs 끈 쪽 11.6%) — 다만 이것도 노이즈 안이다.
**강해졌다고는 못 하고, 손해가 없으며 모형이 더 옳아졌다.** 봇 넷이 다 같은 수비
모형을 쓰는 자기대국에서는 수비 개선이 서로 상쇄되기 쉬워, 이 축은 원래 순위로
잘 드러나지 않는다 — 사람과 붙는 실대국에서 의미가 있는 변경이다.

증강 정책도 **순위와 손 값어치를 본다**(`BotDecisionContext.placement`·`handPoints`).
2026-08-05까지 이 문맥에는 판(손패·위협)만 있고 점수판이 없어, 증강은 동1국과 올라스에서
똑같이 발동했다 — 봇의 버림·리치는 이미 순위를 보는데 증강만 못 보고 있었다.
이제 올라스 선두는 점수 증강을 덜 태우고 방어 증강을 더 태우며, 올라스에 까는 포석은
값이 0이 된다(회수할 국이 없다).

**증강 정책은 의도로 쓴다 (2026-08-05).** 정책 62개 중 **23개가 "제시되면 무조건
발동"** 한 줄이었고, 발동 강도를 밝힌 것은 2개뿐이었다. 타이밍을 신경 쓴 소수는 각자
자기 파일에 같은 조건문(`!someoneRiichi && turnCount < N → null`)을 복붙해 두고
있었다 — 증강이 늘면 그 복붙도 함께 늘어난다(§1의 목표가 봇 쪽에서 깨지는 지점).

**정책 63개 전부**가 이 형태다(손수 쓴 `choose` 0개 — 커버리지 테스트가 잡는다).
지금 정책은 둘만 말한다.

```ts
bot: plan({
  intent: "inform",                                    // 무엇을 하는 물건인가
  pick: ({ options }) => options.find(...) ?? null,    // 어느 선택지인가
})
```

"지금이 때인가"는 증강이 아니라 **판**의 문제라 `content/augments/botPlan.ts`가 한
곳에서 답한다(`readiness`). 의도는 일곱 — `win · defend · advance · score · inform ·
disrupt · setup` — 이고 각각 판의 어떤 값에서 적기가 나오는지가 정의돼 있다
(방어는 위협, 값 올리기는 손의 완성도, 정보는 "쓸 데가 있는가", 포석은 남은 시간).
강도(`BOT_WEIGHT`)도 의도에서 나오므로 정책이 숫자를 직접 쓰지 않는다. 타이밍 모델이
증강의 성질과 안 맞으면(나쁜 손이 곧 발동 조건인 갈아엎기류) `fleeting: true`로 적기
판정을 건너뛴다 — 그 예외가 코드에 드러나 있는 것이 복붙보다 낫다.

**재는 자리 (2026-08-05).** 봇 재작성은 전부 단위 테스트와 장면 시나리오로만 검증됐고,
"그래서 더 잘 두게 됐는가"는 한 번도 재지 않았다. 그래서 상수들(`PUSH_HORIZON`,
`DEAL_IN_SCALE`, 원형표)이 전부 **근거를 대고 고른 값**이지 맞춰서 나온 값이 아니다.
`bot/arena.ts`가 봇끼리 판을 돌려 코어의 `StatsTracker`(실제 전적 화면과 같은 계산)로
집계한다. 시드 하나로 전부 재현되므로 A/B 차이가 변경 때문인지 운 때문인지 갈린다.

    npm run arena -- --games 40 [--mode tonpuu] [--seats attacker,defender,...] [--augments]

첫 측정(동풍전 24판, 원형 고정)에서 바로 드러난 것: **후로율 7.7~16.9%** — 사람의
30~40%에 크게 못 미친다. 유국률 26.8%(실측 ~17%)도 같은 원인이다.

**열린 손의 속도 (2026-08-06).** 그 후로율의 원인 하나를 `value.ts`에서 찾았다.
화료 확률의 노텐 구간은 "샹텐 한 단계에 몇 순 걸리는가"를 우케이레 장수로 재는데,
그 식이 **내 쯔모만** 세고 있었다. 닫힌 손에는 맞지만 열린 손에는 틀리다 — 열린 손은
남의 버림패를 펑·치로 가져와 **턴을 쓰지 않고** 전진한다. 그래서 후로한 손과
후로하려는 손의 속도가 체계적으로 낮게 잡혔고, 후로 입찰이 패스에 지곤 했다.
이제 우케이레를 한 종류씩 "부를 수 있는가"로 나눠 센다(또이쯔면 펑, 슌쯔가 될 패면
상가한테서 치). 배수는 대기의 `RON_MULTIPLIER`에서 나오므로 새 상수가 늘지 않는다.

**후로율의 분모는 '국'이다.** `callRate = callRounds / roundsPlayed`이고 `callRounds`는
**국당 최대 1회**로 센다(안깡 제외 — 멘젠이 유지되므로). 사람의 실측 통계 30~40%도
같은 정의라 **직접 비교된다.** 아래의 콜 기회 집계는 분모가 '기회'라 이것과 다른 자다 —
둘을 섞으면 격차의 크기 자체가 틀어지므로 함께 볼 때 주의한다. (실제로 2026-08-06에
이 분모를 의심해 조사 방향이 한 번 흔들렸고, 확인해 보니 처음부터 국당 정의였다.
`packages/core/test/PlayerStats.test.ts`가 이 정의에 못을 박아 둔다.)

실제 대국 조건(원형 무작위)에서 다시 잰 값 — 동풍전 150판·825국: **후로율 13.8~15.3%**
(유국률 27.0%). 사람 30~40%와의 격차는 정의를 맞춰도 그대로 실재한다.

**"더 울게 만들기"는 세 번 반박됐다 (2026-08-06).** 후로율 격차(봇 14~15% vs 사람
30~40%)를 좁히려는 시도가 셋 다 같은 모양으로 끝났다 — **후로율은 사람 쪽으로 가는데
판은 나빠진다.**

| 시도 | 후로율 | 순위 차 | 점수 차 |
|------|--------|---------|---------|
| #136 쿠이탄 게이트 완화 | 8~18% → 23~43% | (유국률로만 측정, 25.6→30.6%) | — |
| #148 같은 게이트 재측정 | 15.0% → 25.3% | −0.0450 ± 0.0399 | −1314 ± 754 |
| 콜 게이트에 역 읽기 연결 | 15.4% → 19.3% | −0.0250 ± 0.0282 | −855 ± 550 |

세 번째는 "게이트가 아는 역이 넷뿐이라 그렇다"는 가설이었다. 게이트는 실제로 열렸고
(역 없음 34.6% → 29.8%, 구조적 거절 83.1% → 77.6%) 그런데도 판은 나빠졌다. 새로
통과한 콜은 EV에서 대부분 다시 걸렸고(실제 콜은 5.4% → 6.0%뿐), 통과한 것은 손해였다.

**그러니 봇이 안 우는 이유는 문턱도 아니고 아는 역이 적어서도 아니다.** 숫자는 전부
`call.ts`의 `yakuPathAfter` 주석에 남겨 두었다 — 네 번째 시도를 막기 위해서다.

**그래서 울고 난 뒤를 처음으로 쟀다 (`bot/openTally.ts`, `--calls`).** 국을 "그 사람이
울었는가"로 갈라 성적을 낸다. 동풍전 40판·217국:

| 갈래 | 국 | 화료율 | 방총률 | 평균 화료 |
|------|-----|--------|--------|-----------|
| 울었다 | 126 | **19.0%** | 11.9% | **3371** |
| 안 울었다 | 742 | 17.4% | 9.2% | **6896** |

**후로 자체는 망가지지 않았다** — 울면 실제로 더 자주 화료한다(속도는 벌린다).
망가진 것은 **값**이다. 울고 난 손이 멘젠 손의 절반 이하다(3371 vs 6896). 거칠게
기대값을 내면 울고 난 국은 겨우 본전이고 안 운 국은 크게 남는다 — 세 번의 "더 울게
만들기"가 전부 실패한 이유가 여기 있다. **더 울면 그 싼 손을 더 많이 두게 된다.**

**다만 이 표는 관찰이지 인과가 아니다.** 울 수 있었던 손과 그렇지 않은 손은 애초에
다른 손이라("싼 손이라 울었다"일 수 있다), 여기서 "후로가 손해다"가 따라 나오지는
않는다. 인과를 재는 자리는 여전히 2:2 대전이고 그쪽이 말하는 것은 "**더** 우는 것은
손해"뿐이다.

이 표가 주는 것은 **어디를 볼지**다. 울고 난 손이 3371점이라는 사실은 그 자체로
개선 여지를 가리킨다 — 후로를 줄이지 않고 그 값을 올릴 수 있다면 순수한 이득이다.
실제로 그 자리가 하나 나왔다: `call.ts`는 콜 후보 여럿 중 하나를 고를 때 **속도만**
봤다(샹텐 → 우케이레 → 적도라). 부른 뒤 손이 얼마짜리가 되는지가 선택에 들어가지
않았으니, `decide.ts`가 경고한 "판단하지 않은 판단"이 여기 남아 있었던 셈이다.
후보를 EV로 고르게 고쳤다(`callValue` 스위치로 재고 걷었다).

**재 보니 중립이다 (2026-08-07).** 1200배패 두 시드에서 +0.0067 ± 0.0028 /
−0.0029 ± 0.0027로 부호가 뒤집혔다. 이유는 발화 빈도다 — 같은 시드로 EV 켜고/끄고
80배패를 돌려 실제로 부른 조합을 비교하니 **콜 990번 중 4번(0.4%)**만 달랐다.
그래도 남긴 것은 그 0.4%가 전부 옳은 쪽이기 때문이다(안커를 깨는 치 대신 남기는 치
등). 판을 강하게 만들지는 않지만 마작으로서 옳고, 고정 우선순위 사슬이 하나 사라진다.

⚠️ **여기서 A/B 방법론이 하나 굳었다.** `callValue`의 첫 시드는 **2.4σ 양수**였다.
그대로 채택했으면 0.4%밖에 안 건드리는 변경을 "유의미한 이득"으로 기록할 뻔했다.
2400판의 2σ도 시드 하나로는 못 믿는다 — **A/B는 항상 시드 둘 이상으로 본다.**
같은 세션의 `dangerVal`(더블리치·일발권 값 교정)도 +0.0129 → −0.0104로 뒤집혀
중립으로 기록했다.

**세 번째 추측 대신 세는 쪽을 만들었다 (2026-08-06).** 후로율 격차의 원인을 두 번
추측해 두 번 다 틀린 뒤(아래), `bot/callAudit.ts`로 **콜 기회가 어느 관문에서 걸리는지**
집계한다. 첫 측정(동풍전 30판·기회 2152회):

| 결말 | 비율 | 펑가능 | 치뿐 | 역패기회 | 평균샹텐 |
|------|------|--------|------|----------|----------|
| 울었다 | 5.4% | 86 | 31 | 61 | 2.01 |
| EV에서 짐 | 11.5% | 180 | 68 | 67 | 1.80 |
| 역 없음 | 34.4% | 234 | 507 | 0 | 2.42 |
| 전진 없음 | 46.1% | 351 | 640 | 1.61 | |
| 멘젠 텐파이 | 2.6% | 25 | 30 | 3 | 0.00 |

**구조적 거절 83.0% · EV 판단 11.5% · 실행 5.4%.** 즉 콜 기회의 대부분은 EV를
계산해 보지도 못하고 관문에서 끝난다 — 값매김을 아무리 고쳐도 그 83%는 움직이지
않는다. 그리고 EV까지 간 것 중 5% 이내로 진 것은 4.0%뿐이라, "판단이 동전 던지기
위에 서 있다"는 짐작은 **데이터가 지지하지 않았다**(손으로 짚은 한 장면이 2.5%였을 뿐).

**쿠이탄 게이트는 두 번 반박됐다 (2026-08-06).** 위 두 낙관을 다 걷어낸 뒤 #136의
게이트 완화(탕야오 요구패 허용 1장 → 3장)를 강함으로 다시 쟀다: 후로율 15.0% →
25.3%로 사람 쪽에 붙었지만 **순위 -0.0450 ± 0.0399 · 점수 -1314 ± 754**로 두 지표
모두 나빠졌다. 봇의 낮은 후로율은 쿠이탄 문턱 때문이 아니다 — 늘어난 콜은 요구패를
두세 장 안고 여는, 느리고 싸고 접지도 못하는 손이다. 숫자를 `call.ts` 주석에 남겼다.

800판 2:2 대전 결과는 **중립**이다 — 순위 차 +0.0063 ± 0.0341(유의미 아님),
후로율 12.6% → 16.0%. 강해졌다고는 못 하고, **손해가 없고 모형이 더 옳아졌다**.
남은 거리(사람 30~40%)는 이 추정이 아니라 `call.ts`의 구조적 문턱에 있다.

**강함은 2:2로 잰다.** 자기대국은 넷이 같은 정책이라 평균 순위가 구조상 2.5로 수렴한다 —
유국률·총 화료율은 '판의 효율'이지 강함이 아니다. 그래서 새 판단을 `bot/flags.ts`의
스위치 뒤에 두고 **같은 탁에 둘을 앉혀** 순위를 견준다.

    npm run arena -- --games 150 --ab yaku2

배패 운이 결과를 덮지 않도록 **같은 배패를 좌우 바꿔 두 번 돌린다**(듀플리케이트
브리지와 같은 방식). 실제로 무해한 스위치로 검사하면 차이가 **정확히 0.0000**이
나온다 — 편향이 구조적으로 없다는 뜻이고, 그래서 0이 아닌 값은 전부 정책 차이다.
표준오차도 이론값이 아니라 배패별 차이의 표본에서 낸다.

**성격은 원형에서 나온다 (2026-08-05).** 예전에는 성격값 넷을 각각 따로 뽑았다.
그러면 앞뒤가 안 맞는 사람이 나오고(저돌적인데 아무것도 안 울고 다마텐만 고르는 봇),
독립 난수를 평균 근처로 뽑으니 결국 **넷 다 비슷해졌다**. 지금은 원형 하나를 뽑고
거기에 작은 흔들림만 준다 — 원형끼리는 뚜렷이 다르고, 같은 원형의 두 봇은 미묘하게
다르다. 원형의 값들은 **한 사람으로서 얽혀 있다**(타점형은 손을 안 열고 참을성도 높다).

성격은 어떤 판단 **분기**도 만들지 않는다. 전부 이미 있는 계산에 곱해지는 저울이다 —
`aggression`은 밀기/접기 저울, `callLoose`는 콜 EV, `riichiLoose`는 리치 EV,
`valueBias`는 타점/속도 기울기, `patience`는 증강 발동의 값, `sujiTrust`는 **스지를
얼마나 믿는가**, `noise`는 **값이 엇비슷한 후보 사이에서만** 흔들리는 폭, `bluff`는
안전도가 같은 후보 중 세 보이는 쪽을 고르는 크기다. 마지막 둘이 '심리'에 해당하는데, 둘 다 **실력을 깎지 않도록 EV 차이로 묶여
있다** — 손해가 뚜렷한 선택은 변덕이 아무리 심해도 후보에 들어오지 않는다.

허세는 이 봇들 사이에서 실제로 통한다: `danger.ts`가 "종반에 중장패를 흘리는 손"을
텐파이 신호로 읽으므로, 접은 국에 일부러 중장패를 흘리는 봇은 다른 봇을 물러서게 한다.

**스지도 성격이다 (2026-08-06).** 스지가 량면 론을 지운다는 것까지는 규칙이지만,
"그래서 이 패를 내도 되는가"는 판단이고 사람마다 갈린다. 공격형은 스지를 밀 구실로
쓰고(`sujiTrust` 0.9), 수비형은 현물이 있는 한 스지에 손을 대지 않는다(0.28) —
같은 양스지 5를 공격형은 2.9%로, 수비형은 5.3%로 읽는다. 이 값도 분기가 아니라
`suji.waitFactor`가 지우는 량면 몫에 곱해지는 저울이다.

**저울은 이어져 있었지만 너무 좁았다 (2026-08-22, QA 2차 봇 감사 확정 3).**
위의 두 문단은 오래 **약속에 그쳐 있었다.** 같은 장면을 여섯 원형에게 주고
`bidDiscard`를 견주니, 밀기/접기가 갈려야 하는 바로 그 장면(p1 리치 · 텐파이 근처 손)에서
**91.3%가 같은 패**였다. 평시에는 `defender↔balanced`가 300장면 중 1건만 갈렸다.

원인은 **축이 안 이어져 있어서가 아니다.** 여덟 축을 전수로 훑으면 전부 어딘가에서
읽힌다 — `aggression`은 `discard.scales`·`call.evOfCall`·`kan`, `callLoose`는
`call.ts`의 식욕, `riichiLoose`·`valueBias`·`bluff`·`noise`는 `discard.ts`,
`patience`는 `BotAgent`의 증강 발동, `sujiTrust`는 `read.ts` → `danger.tileRisk` →
`suji.waitFactor`. 위 "2.9% 대 5.3%"도 코드가 실제로 그렇게 계산한다.

문제는 **폭**이었다. 밀기와 접기의 비교는 결국 이 부등식이고(안전패의 기대 실점은 0),

    (위험패의 획득 − 안전패의 획득) > 위험패의 기대 실점 × PUSH_HORIZON × (loss/gain)

`loss/gain` 비가 곧 "이만큼 벌 수 있어야 민다"의 문턱 배율이다. 공격성이 저울에 주는
폭이 0.6이면 그 비가 공격형 0.74 · 수비형 1.74 — **2.4배**뿐이다. 실측에서 후보들의
획득 격차는 보통 수백 점인데 기대 실점은 100~230점이라, 2.4배로는 argmax가 거의
안 뒤집힌다.

**그냥 넓혔더니 강함이 깎였다 — 그리고 왜인지가 흥미롭다.** 폭 1.4를 그대로 켜고
아레나 2:2를 돌리니 **−0.15 ± 0.07**(유의미)로 나빠졌다. 표를 보면 무엇이 깨졌는지가
그대로 보인다: **수비형 넷 탁에서 리치율이 18.4% → 10.2%로 무너졌다.**

원인은 밀기/접기 판단이 아니라 **크기**였다. 이 EV에서 저울을 안 타는 절대 상수가
하나 있다 — `RIICHI_COST`(1000점 공탁). 수비형은 `gain`이 0.51로 줄어드니 같은 공탁이
사실상 **1961점**이 되어 리치가 아예 성립하지 않았고, 공격형은 `gain` 1.49라 공탁이
671점으로 싸져 아무 리치나 걸었다. 성격이 아니라 **저울의 부작용**이다.

그래서 저울을 고쳤다: **성격은 이제 `loss/gain` 비만 바꾸고 크기는 안 바꾼다**
(`scales`가 성격이 만든 크기 `norm`을 도로 나눈다). EV 전체를 같은 양수로 나누는
것이라 밀기/접기 argmax는 한 치도 안 변하고, 절대 상수에 대한 왜곡만 사라진다.
순위 압박(`riskAppetite`)은 따로 재서 고른 값이라 크기까지 바꾸던 **종전 동작 그대로**
둔다 — `aggression`이 정확히 0.5인 균형형·타점형에서는 이 함수가 예전과 완전히 같다.

**그리고 미는 쪽은 안 넓힌다.** 공격형은 폭을 0.6·1.0·1.4·1.8 어디에 두어도
**밀기율이 78.2%에서 꿈쩍하지 않는다**(전부 68/87) — 안전패가 애초에 더 쓸모 있는
장면은 성격으로 뒤집히지 않으므로 미는 쪽은 포화한다. 그런데 공격형 넷 탁의 아레나는
넓힌 쪽이 꾸준히 열세라고 답했다. **얻는 것은 없고 잃기만 하는 방향**이다.

| 탁 (동풍전 150배패 × 좌우 교대, seed 4242) | 넓힌 쪽의 순위 차 |
|---|---|
| 공격형 넷 · 폭 1.0 · 정규화 없음 | **−0.1500 ± 0.0689** (유의미하게 나쁨) |
| 공격형 넷 · 폭 1.4 · 정규화 | **−0.0967 ± 0.0695** (여전히 나쁜 쪽) |
| 수비형 넷 · 폭 1.4 · 정규화 없음 | **−0.1467 ± 0.0715** (유의미하게 나쁨 — 리치 붕괴) |
| 수비형 넷 · 폭 1.4 · 정규화 | **−0.0200 ± 0.0675** (차이 없음. 리치율 16.4 → 18.8%) |

그래서 최종형은 **비대칭 + 정규화**다: `discard.AGGRESSION_SPAN_PUSH` 0.6 ·
`AGGRESSION_SPAN_FOLD` 1.4. 수비형의 비는 1.74 → **2.92**(8.5배 폭)가 되고 공격형은
예전 그대로다.

| 장면 묶음 (150장면, seed 4242) | 여섯 원형이 갈린 비율 | attacker↔defender | defender↔balanced |
|---|---|---|---|
| 평시 · 무작위 손 | 19.3% → **30.7%** | 4.0% → **24.0%** | 0.7% → **16.7%** |
| 평시 · 텐파이 근처 손 | 8.0% → **13.3%** | 5.3% → **12.7%** | 5.3% → **8.7%** |
| 위험(p1 리치) · 무작위 손 | 3.3% → **8.7%** | 2.0% → **7.3%** | 0.7% → **6.0%** |
| **위험 · 텐파이 근처 손** | 8.7% → **24.7%** | 8.7% → **24.7%** | 4.0% → **20.0%** |

밀기율(현물을 손에 들고도 비현물을 낸 비율)은 위험·텐파이 근처에서
공격형 78.2%(그대로) · 수비형 67.8% → **52.9%**. 즉 **차이가 10.4%p → 25.3%p**.

접는 쪽을 1.8까지 넓히면 갈린 비율이 31.3%까지 가지만 수비형이 실점을 실제의 11배로
세어 과도하게 접기 시작한다. 1.4는 **더 넓혀도 갈라짐은 조금 늘고 강함만 깎이는** 지점이다.

되돌리는 스위치는 `narrowProfile`(`bot/flags.ts`)이다 — 폭을 좌우 0.6으로 되돌리고
정규화도 끈다. 성격 스위치는 **원형을 고정해야** 잰다: `--ab`의 기본 좌석은 균형형
넷인데 균형형은 `aggression`이 정확히 0.5라 폭을 바꿔도 저울이 같아 차이가 구조적으로
0이 나온다.
성질 검사는 `packages/server/test/BotArchetypePlay.test.ts`,
전후 수치 전문은 `qa-lab/round2/bot-archetype-FIXED.md`.

**입찰 코어 (2026-08-05).** 예전 `decideNow`는 고정된 우선순위 사슬이었다
(`화료 → 증강 → 깡 → 후로 → 리치 → 버림`). 각 단계가 "한다/안 한다"만 돌려주고
앞 단계가 하겠다면 뒤 단계는 물어보지도 않아서, **봇은 비교를 한 적이 없었다** —
이 펑이 리치보다 이득인지 물을 자리가 구조적으로 없었고, 새 판단은 사슬 어딘가에
끼워 넣어야 했다(그 위치가 곧 판단이 되어 버린다). 지금은 전부 점수로 입찰한다.

| 층 | 행동 | 입찰값의 뜻 | 뽑는 법 |
|----|------|-------------|---------|
| 화료 | 론·쯔모 | — | 무조건 |
| 추가 행동 | 깡 · 액티브 증강 | 안 했을 때 대비 **한계 이득** | 양수(문턱 초과) 중 최대 |
| 턴 소비 | 버림 · 리치 · 후로 · 패스 | 그 뒤 판의 **절대 EV** | 최대 |

남은 층 구분은 취향이 아니라 규칙이다 — 깡과 증강은 턴을 소비하지 않아 다른 행동과
애초에 경쟁하지 않는다(하고 나서 그대로 버릴 수 있다). 그래서 **다마텐도 '울지 않기'도
규칙이 아니라 결과**다: 그쪽 입찰이 이긴 것뿐이다. 증강 정책 115개는 `BOT_WEIGHT`라는
자기 눈금(0~100)을 그대로 쓰고, `augmentPoints`가 두 눈금 사이의 환율이 된다 —
정책을 한 줄도 고치지 않고 같은 축에 올라온다. 모든 입찰에는 `reason`이 붙는다.

## 5.5 Augment System — 증강 하나의 해부도

증강 = **데이터 + Modifier 목록 + Effect 핸들러 목록**. content 패키지의 파일 하나.

```ts
defineAugment({
  id: "cheap_riichi",
  tier: "silver",
  name: "가벼운 선언",
  description: "리치 비용이 500점이 된다.",
  modifiers: [{ rule: "riichi.cost", apply: () => 500 }],
  effects: [],   // 필요하면 Event 훅 등록
});
```

드래프트 (확정된 방식, 2026-07-15 수정):

- **지정된 국의 첫 진입마다 1개씩** (2026-08-04 변경):
  동풍전 동1·동3·동4 **총 3개**, 반장전 동1·동3·남1·남3 **총 4개**.
- 각 플레이어에게 **개인별 랜덤 3개 제시 → 1개 선택**.
- 3개 뽑기도 GameState의 시드 PRNG를 사용한다 (리플레이 보장).
- 스케줄(`HanchanConfig.draftSchedules`)과 드래프트 로직 자체도 Rule/모듈이라,
  이후 "매 국 드래프트" 같은 변형 모드를 설정 변경만으로 실험할 수 있다.
- 한 사람이 3~4개를 동시에 굴린다 — 증강 간 중첩 밸런스는 10_AUGMENT_SYSTEM에서 설계.

  패가 어디서 왔는지가 아니라 지금 무엇인지가 진실. (07·08에서 설계)
- **Prism의 한계 (Issue 003)**: "게임 진행 순서 변경"류는 Game Flow의 페이즈 전이표 자체를
