# 0. 증강 디자인 원칙 — 도파민 리트머스 (2026-07-22 개정)

기술 리트머스(위)와 별개로, 모든 신규 증강은 아래 **디자인 리트머스 4문항**을 통과해야 한다.
(배경 철학은 PROJECT_CHARTER "도파민 우선 원칙" — 감정 목표는 "너 그래 이겨라, 다음 판엔 내가 이긴다".)

| # | 질문 | 탈락 예시 |
|---|------|-----------|
| ① 보이는가 | 발동 순간이 테이블 위에서 연출 가능한가? (배너·컷인·패 변형·바닥 변화 등) | 정산 로그에서만 확인되는 점수 보정 |
| ② 부수는가 | 굳어진 리치마작 상식 하나를 정면으로 깨는가? | 기존 규칙 안에서 수치만 유리해지는 효과 |
| ③ 이야기가 되는가 | 게임 종료 후 "아까 그거 뭐였어?"가 나오는가? | 발동했는지 아무도 모르는 효과 |
| ④ 대응이 되는가 | 전원 공개 전제에서 상대가 플레이를 바꿀 수 있는가? (Rule #4) | 알아도 아무것도 못 하는 절대 효과 |

## 금지 패턴 (노잼 금지 조항)

- **역 현상금**: "~역으로 화료하면 +N점" — bounty_* 계열. 전량 삭제 대상.
- **조건부 패시브 보너스**: "조건 X에서 +N점/+N판" — 조건이 아무리 기발해도 결과가
  숫자 보정뿐이면 금지. (`addHanBonus`/`addWinPointBonus`/`yakuBountyBonus` 헬퍼만 쓰는
  증강은 자동으로 이 부류다.)
- **무선택 상시 보정**: 발동에 선택·타이밍·리스크가 전혀 없는 수치 효과.
  단, 상시여도 **규칙 자체가 바뀌어 플레이가 보이는** 것(사방치기·끝없는 윤회 등)은 허용.

## 허용 방향

패 변형(conjured 연출) · 액티브 클릭 발동 · 새 화료 조건 · 턴/순서 조작 · 바닥·후로 왜곡 ·
리치 개조 · 정보전 · 도박(선택과 리스크가 보이는 것) · 왕패/도라 조작 · 국 구조 변형.
점수 이동조차 "보이는 사건"(강탈·베팅·공탁)으로 연출한다.

## 무페널티 원칙 — 리미트는 횟수로만 (2026-07-22 사용자 확정)

증강을 억제하는 수단은 **발동 횟수**(게임당 N회 / 국당 1회 / 2국당 1회)와
**발동 조건**(자기 턴·텐파이·깡 2회 등)뿐이다. **능력에 붙는 손해는 전부 금지한다.**

- ❌ 위약금·상환·벌점·공탁 몰수 (`-8000`, `실패 시 -2000`, `게임 끝에 -15000`)
- ❌ 역 봉인·행동 금지 (청일색 못 씀, 리치 중 사용 불가, 그 국 화료만 가능)
- ❌ 내 손해로 굴러가는 구조 (내 점수 절반을 걸기, 방총 시 지불 증가, 상대에게 점수 지불)
- ❌ 상대를 이롭게 하는 구조 (내 좋은 패가 상대에게 넘어감, 상대가 내 대기를 완벽히 회피)
- ❌ 나에게 불리할 수 있는 무작위 (무작위 색 통일, 무작위 3장 유출) → **플레이어 선택으로 바꾼다**
- ✅ "게임당 1회뿐이다" — 이미 충분한 제한이다. 그 1회는 **온전히 강력해야** 한다.

**도박형도 예외가 아니다**(2026-07-22 확정). "실패하면 잃는다"는 구조는 발동해 놓고도
손해를 계산하게 만들어 도파민을 깎는다. 도박의 두근거림은 **업사이드의 크기**로 만든다 —
"걸면 크게 딴다"는 남기고 "빗나가면 잃는다"는 뺀다.

**단, 전원 공개는 페널티가 아니다.** 증강 보유·발동이 전원에게 보이는 것은 Rule #4
(항상 대응 방법이 존재해야 한다)의 전제이자 이 게임의 재미 구조다. 정보 공개는 유지한다.

**명시적 예외 — 뚫린 천장의 초과분은 타가가 낸다** (2026-08-02 사용자 지시).
이 원칙이 막는 것은 **보유자 자신의 손해**다. "내 화료점이 올라간 만큼 상대가 더 낸다"는
보유자에게 아무 손해가 아니고, 오히려 뱅크 발행이던 시절엔 천장을 뚫어도 아무도 아파하지
않아 사건이 성립하지 않았다. 구현은 `content/util.ts`의 `addWinPointTransfer`이며,
**사용자가 지정한 증강에만** 쓴다 — 나머지 화료 보너스는 전부 뱅크 발행(`addWinPointBonus`)
그대로다.

## 확정 보상 단위 — 점수 금지, **판수로만** (2026-07-26 사용자 확정)

증강이 능력과 별개로 얹어 주는 확정 보상은 **점수가 아니라 판수로만** 쓴다.
"화료 시 +2000점"은 **"화료 시 2판 추가"**로 바뀌었고, 표기는 다시 아래 규약을 따른다
("리치를 2판으로 취급한다" / "+2판을 얻는다").
신규 증강도 예외 없이 이 단위로 설계한다 — 점수 단위(2000/4500/6000)는 **폐기**다.

- **왜**: ① 마작 플레이어에게 "판"은 손의 크기를 말하는 유일한 언어인데 정산 로그에 뜬금없는
  정액이 섞이면 손 가치를 읽을 수 없다. ② 정액은 저판 손에는 크고 만관 손에는 티가 안 나
  체감이 뒤집힌다. 판수는 손 크기에 비례해 **커질 손은 더 크게** 터진다.
- **표기 규약 (2026-07-26 사용자 확정)** — 판수를 **어떻게 쓰는지**까지 통일한다.
  "N판이 붙는다 / 얹힌다 / 추가된다"는 전부 금지다.

  | 상황 | 표기 | 예 |
  |------|------|-----|
  | 관련 역이 **있다** | **"〈그 역〉을 N판으로 취급한다"** | 개문선언 "리치를 2판으로 취급한다" · 숨은 칼날 "리치를 2판으로 취급한다" · 절벽 위에 피어난 꽃 "영상개화를 4판으로 취급한다" · 탕야오 해방 "탕야오를 2판으로 취급한다" |
  | 역이 **1판 그대로**면 판수를 말하지 않는다 | **"〈그 역〉으로 취급한다"** | 혼 사냥 "리치로 취급되며" · 고요한 리치 "리치로 취급되어" |
  | 관련 역이 **없다** | **"+N판을 얻는다"** | 철벽 "+3판을 얻는다" · 예지 "+2판을 얻는다" · 해저의 지배자 "+3판을 얻는다" |

  관련 역이 있으면 **그 역의 표준 판수를 흡수해서** 쓴다 — "리치를 2판으로 취급"은 표준 리치
  1판과의 차이인 +1판만 정산에 얹는다는 뜻이다. 구현 상수도 `OPEN_RIICHI_HAN = 2` /
  `STANDARD_RIICHI_HAN = 1`처럼 **취급 판수와 표준 판수를 따로** 두고 차이를 얹는다
  (`cliff_bloom`의 `BLOOM_RINSHAN_HAN`/`STANDARD_RINSHAN_HAN`이 원형).

- **구 정액 → 판 환산 이력** (2026-07-26 통일 시점의 1차 환산과, 실측 후 재조정):

  | 구 표기 | 1차 환산 | 확정 |
  |---------|----------|------|
  | +2000점 | 2판 | **2판** (무형화료·개문선언은 이후 "역 N판 취급"으로 표기 변경) |
  | +4500점 | 3판 | **2판** (예지·정적의 손) / **3판** (해저의 지배자 — 발동이 게임당 한 번 볼까 말까) |
  | +6000점 | 4판 | **3판** (철벽) / **4판** (카운터) |
  | 스택 1000점당 | 스택당 1판 | **스택당 1판** (미래를 보는 자 — 2026-08-02 발동을 3순에 1회로 조이며 환율 복구) |

  ⚠ 1차 환산은 "3판30부 자 론 = 5800"을 전제로 잡았는데 **실제 값은 3900**이라, 실측해 보니
  전 항목이 구 정액의 1.5~3배였다(오야는 추가로 1.5배). 새 증강의 판수를 정할 때는
  **`calculateScore`로 실측**하고, 저판 손·오야 케이스를 반드시 함께 본다.

- **구현**: `content/util.ts`의 `addWinHanBonus(ctx, han)` 하나만 쓴다
  (core 표준 증강은 `standardAugments.ts`의 동명 로컬 헬퍼).
  내부적으로 `winPointsWithExtraHan`으로 환산한 **뱅크 점수**를 정산에 얹으므로,
  판이 올랐어도 **상대가 더 내지는 않는다** — 위 무페널티 원칙과 충돌하지 않는다.
  승자의 실제 부수·역만·오야 여부를 그대로 쓰기 때문에 만관/하네만 상한도 정확히 반영된다.
- ⚠ **합산 주의**: 판수는 상한 구간에서 비선형이라 여러 판 보너스가 겹치면 정액 시절보다
  세진다. 확정 보상은 **증강당 한 줄**로 두고, 겹칠 것 같으면 **기존 역의 판수를 올려** 표현한다 —
  `cliff_bloom`이 선례다(3판+4판=7판 → **"만개 국의 영상개화를 4판으로 취급"**, 표준 1판 대비 +3판).
  `tanyao_break`도 같은 방식으로 접었다(1판 역 + 화료 시 +2판 → **"탕야오를 2판으로 취급"**).
- ⚠ **역만에는 얹히지 않는다**: `calculateScore`는 `yakumanCount > 0`(및 셈수역만)이면 판수를
  무시하므로 환산 차액이 정확히 0이다. 정액 시절엔 역만 위에도 얹혔으니 동작이 바뀐 지점이다
  (예: 철벽으로 국사를 후리텐 론 → 구 +6000, 현재 +0). 이미 상한인 손이라 그대로 둔다.
- **예외 (판수로 바꾸지 않는 것)**: 화료 보너스가 아닌 정액 — 유국 이전(`always_tenpai`
  노텐당 2000), 본장 배율(`honba_hunter`), 선지급·강탈(`devils_advance`), 판돈(`all_or_nothing`),
  리치 공탁 1000, 승리 조건 점수(`unification`). 이것들은 애초에 "화료에 얹는 보상"이 아니다.

기존 카탈로그의 삭제/개편/유지 판정과 신규 증강 백로그는 **16_AUGMENT_REDESIGN** 참조.
증강별 정량 지표(난이도·사기성·도파민·신박함·추가 보상)는 **17_AUGMENT_BALANCE**가 단일 진실 —
증강을 추가·삭제·개편하면 17번 표를 같은 커밋에서 갱신한다.

# 1. 증강 하나의 해부도

증강은 **데이터 + install 함수**다. install은 획득 시 각 Registry에 자기 능력을 등록한다.

```ts
defineAugment({
  id: "iron_wall",
  tier: "gold",
  category: "shape",          // 계열 — 필수. 카드 칩·pill 아이콘·발동 컷인 색이 이 값으로 갈린다
  name: "철벽",
  description: "후리텐을 무시하고 론할 수 있다.",
  detail: "자신이 이미 버린 패로도 상대의 버림패를 잡는다.\n\n… (도감 상세 설명, 여러 문단 허용)",
  install(ctx) {
    ctx.setHolderRule("win.furiten.enabled", false);   // 이 증강 보유자에게만
  },
});
```

- `description`는 드래프트·pill에 쓰는 **한 줄 요약**, `detail`(선택)은 증강 도감(15 §도감)에
  노출되는 **여러 문단 상세 설명**이다. `detail`은 엔진/드래프트가 읽지 않는 순수 표시용이며,
  카탈로그 메시지(`AugmentCatalogEntry.detail`)로 클라이언트에만 전달된다. 없으면 도감은
  `description`으로 대체 표시한다. 콘텐츠 팩 70종은 모두 `detail`을 가진다(표준 증강은 미보유).

- `category`(필수)는 증강의 **계열**이다 — 등급이 폐기된 뒤 남은 유일한 시각 분류이며,
  드래프트 카드 칩·이름표 pill 아이콘·발동 컷인 색(`--fx-color`)이 전부 이 값 하나로 갈린다.
  9종: `scoring`(점수) · `info`(정보) · `hand`(손패 조작) · `shape`(화료형) · `call`(후로) ·
  `riichi`(리치) · `defense`(수비) · `disrupt`(교란) · `etc`(기타).
  **`etc`는 증강 자체를 다루는 메타 능력(재장전)만** — 애매하다고 여기에 넣지 말 것
  (`augment_category.test.ts`가 막는다). 2026-07-26에 클라이언트의 id 관례 휴리스틱을
  폐기하고 증강 정의로 끌어올렸다 — 그전엔 신규 증강 39종이 조용히 "기타"로 새고 있었다.
  계열은 카탈로그(`AugmentCatalogEntry.category`)로 클라이언트에 전달된다. 발주 규격은 docs/19 §4.1.

`install(ctx)`가 받는 것:

| 도구 | 하는 일 | 뒤에서 |
|------|---------|--------|
| `ctx.setHolderRule(rule, value)` | 보유자에게만 규칙 값 고정 | RuleRegistry.addModifier (player-scoped) |
| `ctx.reaction(on, react)` | 이벤트 후 새 이벤트 방출 | EffectRegistry.register |
| `ctx.interceptor(on, fn)` | 이벤트를 수정·취소·대체 | EffectRegistry.register |
| `ctx.grantAugments(pick)` | **다른 증강을 보유자에게 지급** (화수분) | augmentGrant 액션 + installAugment |
| `ctx.engine` | 그 외 모든 것 (새 Action·Zone·역…) | 직접 접근 |

- `ctx.grantAugments`는 지급형 증강 전용이다(2026-08-04, 화수분). 후보는 카탈로그 전체에서
  **자기 자신·이미 보유·상호 배제(conflicts)·모드 부적합**을 뺀 목록이며, 선택은 **상태에서
  파생된 결정론적 난수**여야 한다(`Math.random` 금지 — 리플레이가 갈라진다).
  지급은 **인스턴스당 한 번**이다: 결과가 `augmentGrantKey`로 상태에 남아, 재구성
  (`rebuildAugments`)에서 install이 다시 불려도 다시 뽑지 않는다. 카탈로그를 넘기지 않은
  경로(최소 테스트 게임)에서는 조용한 no-op다.

## "뽑자마자 자동 발동, 이번 국만" (2026-08-04)

드래프트는 국과 국 사이에만 열리므로, 획득 뒤 **처음 시작되는 국**이 곧 사용자가 말하는
"이번 국"이다. 공용 배선은 `content/util.ts`의 `armOnNextRound(ctx, id, onArm?)` /
`armedNow(state, id, holder)` 한 쌍이다 (초읽기·눈먼 총알·음양 반전).

- install 시점의 `roundKey`를 클로저에 담으면 안 된다 — 그때 상태에 남아 있는 것은 **직전 국**이고,
  install은 재구성에서 다시 불린다. 상태에 **한 번만 쓰는**(이미 있으면 건드리지 않는) 방식이라
  리플레이·재개에서도 같은 국이 잡힌다.
- 공개 채널 표시는 **반드시 `onArm`으로** 낸다. 같은 `ROUND_STARTED`에 리액션을 하나 더 달면
  그 리액션이 보는 state에는 아직 표식이 반영되지 않아 `armedNow`가 항상 false다.

- 모든 등록의 `source`는 인스턴스 id(`aug:<player>:<augmentId>`)다.
  증강 파괴가 필요해지면 `removeBySource`로 규칙·훅이 한 번에 사라진다.
- **install은 순수하지 않다** (Registry를 바꾼다). 그래서 GameState가 아니라
  DraftController가 픽 직후에 호출한다 (§4).

## 등급 폐기 결정 (2026-07-22, 52차 사용자 확정)

**등급(Silver/Gold/Prism)을 없앤다.** 모든 증강이 같은 수준의 도파민 —
"프리즘 느낌" — 을 줘야 하며, 약한 등급이라는 도피처를 두지 않는다.

- 등급 폐기 시 **`gambler`(전환 : 골드)·`gambler_pro`(전환 : 프리즘)는 존재 이유가 사라진다** —

- 드래프트의 등급 가중치·등급 통일·등급 고갈 폴백도 함께 걷어내고, **균등 비복원 3지선다**로
  단순화한다(아래 §3의 등급 관련 규칙은 그때 삭제).
- 코드상 `AugmentDef.tier`와 `RuleLayer`는 **합성 우선순위**로는 계속 필요하다 —
  표시용 등급만 없애고 Layer는 "이 증강이 규칙 합성에서 몇 번째로 말하는가"로 남긴다.

## 전역 UX·연출 규약 (2026-07-22, 52차 사용자 확정)

신규·기존 구분 없이 **모든 증강**에 소급 적용한다.

### 1) 패를 고르는 증강은 전부 "새 탭"(모달)

액티브 버튼 자리에 후보 버튼을 늘어놓지 않는다. **실제 패를 눈으로 보고 고르게** 한다.

- 구현 패턴은 `.rinshan-pick-overlay` 모달을 재사용한다 (절벽 위에 피어난 꽃·
  등가교환·미래를 보는 자가 이미 이 방식). 프롬프트가 열리면 자동으로 뜨고, "닫기"로 접으면
  `.rinshan-reopen` 플로팅 버튼으로 다시 열 수 있다.
- **고를 패가 없는 액티브는 모달을 쓰지 않는다.** 밑장빼기(`bottom_deal`)처럼 payload가 빈
  예약형은 액티브 버튼 하나로 끝난다 — 보여 줄 것은 선택지가 아니라 **결과가 어디서 오는지**
  이므로, 손패 위 스트립(`.bottom-deal-strip`)으로 패산 밑 3장을 상시 띄운다.
- 대상이 **손패 1장**이든 **왕패**든 **바닥**이든 동일하다 — 후보를 텍스트 버튼으로 내는 것은
  금지. 최소한 그 패의 실제 그림이 보여야 한다.
- 예외는 **패가 아닌 것을 고르는 선언형**(예: 오야 찬탈·천하무적)뿐 — 이건 버튼이 맞다.

**모달 세부 규약 (2026-07-26 사용자 지적 반영, 전 모달 소급)**

- **패는 크게.** 25px짜리 미니 패로는 무엇을 고르는지 안 보인다. `.aug-pick-rows`가
  `--pick-tile-w`(≈34~50px)로 모달 안 `.tile-mini`를 일괄 확대한다 — 개별 모달에서
  크기를 손대지 말고 이 변수를 쓴다. `.rinshan-pick-*` 계열은 이미 `size="hand"`라 해당 없음.
- **내 손패는 정렬해서.** 모달에 펼치는 내 손패는 Zone 순서(뽑은 순)가 아니라 `sortTileIds`로
  정렬한다 — 게임판의 손패와 배열이 다르면 같은 패를 눈으로 못 찾는다. 변형 미리보기
  (단색 세계)는 **바뀐 뒤 모습 기준**으로 정렬한다. 바닥(버림 순)·왕패(자리 순)처럼
  순서 자체가 정보인 줄은 그대로 둔다.
- **왕패를 그리는 모달은 빠진 영상패를 빈 칸으로 남긴다.** 깡의 영상 쯔모는 보충되지 않아
  왕패가 줄어드는데(07 §2), 남은 패만 촘촘히 그리면 몇 장 썼는지가 안 보이고 표시패 열이
  통째로 왼쪽으로 밀려 보인다. `rinshanSpentOf(view)`만큼 빈 자리를 앞에 그려 14칸 배열을
  유지한다(`.rinshan-slot-spent` / `.aug-pick-tile-spent`). 자리 라벨은 `deadWallSlotInfo`가
  **뒤에서부터** 계산하므로 상수 인덱스를 쓰지 말 것.
- **턴이 지나면 탭도 닫는다.** 프롬프트에서 그 액션이 사라지면 모달을 자동으로 닫는다
  (`ActiveAugmentControl`의 pickModal 자동 해제 effect). 이미 끝난 선택창이 남아 있으면 안 된다.
- **횟수가 여러 번인 증강은 한 번에 여러 쌍을 고르게.** 고른 쌍을 모달 안에 쌓아 두었다가
  확정에서 큐에 넣고, **프롬프트가 갱신될 때마다 하나씩** 보낸다(액션 1개 = 교환 1회).
  연달아 보내면 두 번째가 갱신 전 프롬프트에 실려 거부되므로, 보낸 프롬프트를 ref로 기억해 막는다.
  선례: 왕패의 주인(`dw_swap`).

### 2) 플레이어를 고르는 증강은 실제 지목 연출

이미 구현된 경로를 그대로 쓴다 — 액티브 버튼으로 무장 → **상대 이름표를 직접 클릭**
(`ARM_MODE: "opp"`), 지목당한 사람에게는 전용 전면 컷인 + 상태 뱃지 + 지목 관계 표식
(16 §2 지목형 공통 연출 규칙).

### 3) 증강 연출은 치·펑·깡과 확실히 달라야 한다

후로 연출은 "쿵" 하고 패가 꽂히는 **물리적·타격적** 톤이다. 증강은 그 반대 —
**초자연적·순간적**이어야 한다.

- 기준 이미지: **번개가 화면을 스치듯 지나간다.** 짧게(150~300ms) 번쩍이고 사라지는 광원,
  화면을 가로지르는 섬광 띠, 패 위를 훑고 지나가는 스캔라인 계열.
- 후로 연출의 어휘(shake·충격파 링·먼지)는 증강 연출에서 **주역이 되면 안 된다**.
  써야 한다면 번쩍임 뒤의 잔향으로만.
- **증강마다 전용 연출을 반드시 만든다.** 기본 컷인으로 때우지 않는다 —
  "이 증강이 터졌다"를 색·모션만 보고 구분할 수 있어야 한다.

### 4) 효과음은 자연스럽게

현재 사운드가 "턱턱 퍽퍽"으로 딱딱하다. 어택이 너무 빠르고 클릭 노이즈가 남는 탓이다.

- 어택을 완전히 0으로 두지 말고 짧은 페이드인(3~8ms)을 준다 — 클릭 노이즈의 주범.
- 릴리스는 지수 감쇠로 충분히 길게(현재보다 1.5~2배) 빼서 꼬리를 남긴다.
- 사각파·톱니 위주의 배음을 줄이고 삼각파/필터드 사인 쪽으로 부드럽게.
- 증강 발동음은 후로음과 **음색 계열 자체를 분리**한다 — 후로는 타악, 증강은
  벨·글리치·역재생(swell) 계열.

## 등급 = 프리즘의 세기 (2026-07-22 사용자 확정) — 위 폐기 방침에 따라 곧 삭제

**모든 등급이 프리즘이다.** 등급은 "안전한가 위험한가"가 아니라
**리치마작의 상식을 얼마나 크게 부수는가**의 차이다.

| 등급 | Layer | 정체성 | 기준 |
|------|-------|--------|------|
| Silver | 100 | **약한 프리즘** | 규칙을 하나 비튼다. 작지만 분명히 "어, 그게 돼?"가 나온다 |
| Gold | 200 | **애매한 프리즘** | 규칙 하나를 확실히 깬다. 판을 뒤집을 수 있다 |
| Prism | 300 | **확실한 프리즘** | 마작의 대전제를 부순다. 그 판이 이 증강 중심으로 돌아간다 |

- Silver는 "무난한 증강"이 아니다 — **작은 규칙 파괴**다. 수치만 유리해지는 효과는
  등급을 막론하고 §0 금지 패턴에 걸린다.
- 세 등급 모두 **페널티가 없다**(§0 무페널티 원칙). 등급이 낮다고 대가를 치르지 않는다.
  Silver가 약한 이유는 **부수는 규칙이 작아서**이지 손해를 감수해서가 아니다.
- 예: Silver 붉은 손길(손패의 5를 전부 적도라로) — 패를 눈앞에서 바꾼다는 점에서 프리즘의
  축소판이다. Gold 철벽(후리텐 무시 론) — 방어의 대전제 하나를 깬다.
  Prism 우는 국사무쌍(펑으로 국사) — 화료형 자체를 다시 쓴다.

같은 규칙을 여러 증강이 건드리면 (Layer, 획득 순서)로 결정적으로 합성된다 (04·05와 동일).

- 스케줄(2026-08-04 변경): **지정된 국에 첫 진입할 때 1개씩.**
  동풍전 `gameStart(동1)·eastThird(동3)·eastFourth(동4)` = **3개**,

  본장 연장으로 같은 국이 다시 열려도 스테이지당 1회만 열린다(`draftedStages` 가드).
- 각 플레이어에게 **개인별 랜덤 3개 제시 → 1개 선택**. 선택 결과는 **전원 공개**.
- 3개 뽑기: **균등·비복원**. 등급 가중치·등급 통일·등급 고갈 폴백은 2026-07-22(52차)
  등급 폐기와 함께 전부 삭제했다 — 모든 증강이 같은 프리즘급이라 등급으로 확률을 나눌 이유가 없다.
- 제외 대상: 이미 보유 · 스테이지/모드 부적합(`draftStages`·`modes`) · 보유 증강과 상호 배제(`conflicts`).

## 다양성 — 좌석별 후보 칸 (2026-07-26)

한 게임에 증강이 최대한 골고루 나오도록 두 겹을 건다. 둘 다 `DraftController`에 있다.

1. **좌석별 서로 소인 후보 칸(`cellFor`)** — 스테이지가 열리면 제시 가능한 풀을
   `(시드 ⊕ 스테이지)`로 섞어 좌석 순서대로 **겹치지 않는 구간**으로 자르고, 각 좌석은
   자기 칸에서만 3장을 뽑는다. → **같은 스테이지에 두 사람에게 같은 증강이 제시되지 않는다.**
   칸 크기는 `max(choices×6, 18)`로, 보유·상호 배제로 몇 개가 빠져도 3장을 못 채울 일이 없다.
   (스테이지가 4회로 늘어난 2026-08-04에 12→18로 키웠다 — 마지막 스테이지에는 남들이 가진
   최대 9개와 내가 가진 3개가 칸에서 빠지므로 3+9+3=15가 필요하다.)
2. **게임 내 중복 금지(`heldByOthers`)** — 누가 이미 보유한 증강은 아무에게도 다시 제시하지
   않는다. → 한 게임에서 같은 증강을 둘이 갖는 일이 없다.

**왜 칸 계산에 가변 상태를 넣지 않는가**: 칸은 `offerable`(draftStages·modes)만 본다.
보유 증강처럼 국 중에 변하는 값을 칸 경계에 넣으면 **스테이지 도중 누가 픽할 때마다 남의 후보가
흔들려** `pick`의 "제시된 것인가" 검증이 깨진다(정상 픽이 거부된다). 칸이 서로 소이므로
"남이 이번 스테이지에 픽한 증강"은 애초에 내 칸에 없고, 그래서 ①과 ②가 서로를 흔들지 않는다.

**폴백**: 카탈로그가 `좌석수 × 칸크기 + 3`보다 작으면(작은 테스트 카탈로그·극단적 모드 필터)
칸을 못 나누므로 **기존 전역 균등 추첨으로 돌아간다** — 그때는 겹침을 보장하지 못하지만
**빈 드래프트는 여전히 없다**. 칸이 말라붙는 극단적 경우의 보충도 같은 이유로 남겨 두되,
보충 경로에서는 `heldByOthers`를 적용하지 않는다(적용하면 결과가 흔들려 픽 검증이 깨진다).

실측(108종 카탈로그·반장전 500게임): 예전에는 **38.2%의 게임에서 12장 중 겹치는 제시**가
있었고, 지금은 **0%**다. 500게임에 등장한 서로 다른 증강은 107종(반장전 전용 필터로
`late_bloomer_east` 하나만 빠짐).

## 상호 배제 (conflicts, 2026-07-25)

- `AugmentDef.conflicts`(증강 id 목록)로 **동시에 보유할 수 없는** 증강을 선언한다.
  드래프트에서 한쪽을 이미 가진 플레이어에겐 다른 쪽을 제시하지 않는다
  (`DraftController.excludeFor`가 보유·스테이지/모드 제외와 함께 처리).
- **관계는 대칭**이다 — 한쪽에만 선언해도 `excludeFor`가 두 방향을 함께 보므로
  역방향(그 증강 → 진짜 용)도 자동으로 막힌다. 상태(보유 증강)에서만 파생되므로
  리플레이에 안전하다.
- 용례: **진짜 용**(5멘쯔·17장)은 `decompose`가 치토이·국사를 `totalSets===4 && hand===14`
  에서만 열거하는 탓에 14장/4멘쯔 전제 특수형을 전부 무력화한다 — 죽은 픽(조용한 무효)이나
  소프트락(우는 국사: 표준·국사 양쪽 봉인)이 되므로 `open_kokushi·giant_god·royal_kokushi·
  async_chiitoi·mixed_nine_gates·void_kan`을 conflicts로 잠근다.
- **손패를 통째로 옮기는 증강**(자리 바꿈·통째로 바꾸기)은 배패 장수가 다른 상대와의
  교환을 conflicts가 아니라 **액션 레벨 `util.sameHandSize` 가드**로 막는다 — 다른
  플레이어가 진짜 용을 보유해 **대상으로 지목**하는 교차 케이스는 드래프트 배제로 못 막기
  때문이다. 판정은 `util.sameHandSize` 한 곳으로 통일한다(사본 분기로 가드가 빠지는 것 방지).

- **conflicts는 최후의 수단이다** (2026-07-27, 60차). "한쪽이 다른 쪽을 죽인다"를 발견하면
  먼저 **죽는 쪽을 고쳐** 본다 — 대개 화료형 상수를 하드코딩한 것이 원인이다.
  `cliff_bloom`(`sets = 4 - meldCount`)·`bottom_deal`(`winningKinds`에 opts 미전달)은
  진짜 용 앞에서 조용히 죽고 있었는데, `scoringOptionsOf`/`view.scoringOptions`를 읽게
  바꾸자 **함께 작동**하게 됐다. 배제는 픽 하나를 없애는 것이므로, 공존시킬 수 있으면 그게 낫다.
- **conflicts로 막을 수 없는 것**: 무장해제처럼 **상대 증강을 지목**하는 증강은 드래프트
  배제의 사정거리 밖이다. 진짜 용이 무장해제당하면 규칙만 4멘쯔로 돌아가고 손패는 16/17장으로
  남아 그 국이 하드락이었다 — 이건 §7 무장해제 후처리 훅으로 해결한다.

## 드래프트의 결정성

- 3개 선택지는 **`(게임 시드, 스테이지, 플레이어)`에서 파생된 별도 PRNG**로 뽑는다.
  게임 진행용 PRNG(배패)를 소비하지 않는다 — 선택지는 UI일 뿐, **상태를 바꾸는 것은
  오직 "무엇을 골랐는가"(픽)**이기 때문이다.
- 그래서 리플레이는 픽(AugmentDrafted 이벤트)만 있으면 재현된다. 선택지는 언제든 재계산 가능.

# 4. 상태·이벤트·설치의 관계

**GameState가 진실이다.** `PlayerState.augments`(증강 id 목록)가 SSOT.

```
draftPick (Action)
   ↓ toEvents
AugmentDrafted (Event) ──Reducer──▶ state.players[p].augments += id   (순수)
   ↓ (DraftController가 픽 직후)
installAugment(engine, def, holder)  ──▶ Registry에 능력 등록          (부수효과)
```

- 이벤트 로그를 재생할 때도 AugmentDrafted 시점에 install을 호출해야 뒤 이벤트가
  증강 효과를 본다. `rebuildAugments(game, catalog)`가 state.augments 전체를 재설치한다
  (게임 재구성·리플레이용).
- Registry는 GameState.augments에서 **파생**된다 — 이 규율이 리플레이 안정성을 준다.
- **AugmentOffered (통계 전용 이벤트)** : `draftOffer` 액션 → `AugmentOffered`(no-op reducer,
  상태 불변). `DraftController.recordOffer`가 픽보다 먼저 고정 순서로 제시(3지선다)를 로그에
  남겨 픽률·등급 분포 통계를 만든다(§14). 게임 상태·리플레이 결과에는 영향 없음.
- **드래프트를 거치지 않는 지급 (49차, 증강 테스트용)** : `HanchanConfig.presetAugments`
  (첫 국 배패 전 좌석별 사전 지급)와 `HanchanController.grantAugment(player, id)`
  (진행 중 즉시 지급)도 같은 경로(draftPick 액션 → AugmentDrafted → installAugment)를 탄다.
  스테이지 완료 플래그(`draft:done:*`)만 찍지 않아 정상 드래프트 진행과 섞이지 않는다.
  국 도중 지급은 그 국의 배패·국 시작 시점을 되돌리지 못하므로, 배패에 개입하는 증강은
  사전 지급(새 판)으로 확인해야 한다. 관리자 UI·초기화 흐름은 docs/15 §5c.

# 5. 표준 증강 4종 (등록 API 실증)

각각 **서로 다른 등록 지점**을 써서 "엔진 수정 없이"를 증명한다.

| id | 등급 | 효과 | 등록 지점 |
|----|------|------|-----------|
| iron_wall (철벽) | Gold | 후리텐 무시하고 론 가능 | Rule Modifier (win.furiten.enabled) |
| open_riichi (개문선언) | Prism | 후로한 손으로도 리치 가능 | Rule Modifier (riichi.requiresClosed) |
| yakuless_win (무형화료) | Prism | 역 없이도 화료 가능 | Rule Modifier (win.requiresYaku) |
| discard_recall (회수) | Prism | 쯔모패를 버리고 자기 버림패 하나 회수 (게임당 1회) | **새 프롬프트 액션** + augmentData |

- **삭제됨 (2026-07-22, 48차 — §0 노잼 금지 조항)**: cheap_riichi(가벼운 선언, Rule Modifier)·
  tsumo_bonus(쯔모의 기쁨, Effect Reaction)·vengeance(설욕, Effect Interceptor) 3종.
  전부 보이지 않는 패시브 점수 보정이었다. 여기서 빠진 두 등록 지점(Effect Reaction·
  Interceptor)은 콘텐츠 팩 70종이 대량으로 실증하고 있어 표본을 유지할 이유가 없다.
- 위 3종을 위해 엔진에 새로 판 것은 **규칙 3개**(`win.requiresYaku`,
  `win.furiten.enabled`, `riichi.requiresClosed`)를 표준 규칙에 정의하고,
  표준 액션의 검증이 이 규칙을 **읽도록** 한 것뿐이다. 이제 이 규칙들을 건드리는
  수백 개 증강이 추가 코드 없이 가능하다.
- `discard_recall`은 **차터의 대표 예시("버림패 회수")** 로, 새 플레이어 액션을
  엔진 수정 없이 프롬프트에 노출하는 §6의 확장 지점을 실증한다. 새 이벤트
  `RecallPerformed`와 그 Reducer, 새 액션 `recall`을 install에서 등록하고
  (여러 보유자가 있어도 `has()` 가드로 한 번만), 보유자 턴에 자기 버림패마다
  후보를 제시한다. 손패 수는 보존된다.

# 6. 확장 지점 (✅ 구현됨) 과 남은 과제

## ✅ 새 프롬프트 액션 (2026-07-15 해소)

증강이 새 플레이어 액션을 턴 프롬프트에 노출할 수 있다.

- `ctx.holderTurnOptions(build)` — 보유자 턴에 후보 ActionOption 목록을 제공한다.
  FlowController가 각 후보를 **validate로 다시 걸러** 합법인 것만 제시한다
  (프롬프트의 진실은 언제나 validate — Server Authority).
- 새 액션·이벤트·Reducer는 `ctx.engine`으로 직접 등록한다.
- `discard_recall`이 이 경로를 실증한다.
- **액티브 증강 UI**: 클라이언트는 `AUGMENT_ACTION_TYPES`에 속한 프롬프트 옵션을
  전용 "✦ 액티브 증강" 버튼으로 모은다. 여러 액티브 증강을 동시에 보유해
  후보가 2개 이상이면, 버튼을 누르면 **증강 이름이 붙은 선택 메뉴**가 열려
  원하는 증강의 액티브를 골라 발동한다 (`ACTION_AUGMENT`가 액션→증강 매핑).
  예: `cliff_bloom`(bloom_kan — 영상개화 확정 안깡), `no_retreat`(declare_no_retreat — 리치 전념 선언).

## ✅ 증강 전용 데이터 (2026-07-15 해소)

- GameState에 `augmentData: Record<string, unknown>` (게임 단위, 국이 바뀌어도 유지).
- `AugmentDataSet` 이벤트 + 범용 Reducer로만 변경한다 (SSOT). "1회 한정" 능력이

- **리플레이 주의**: 증강이 등록하는 새 이벤트 타입의 Reducer는 순수 재적용 시에도
  필요하므로, ReplayReader는 `AugmentDrafted`를 만나면 그 증강을 `installAugment`한다
  (드래프트 순서상 새 이벤트보다 먼저 등록됨). 재구성 검증 완료.

## ✅ 콘텐츠 팩 대량 확장 (2026-07-16 해소)

`@majak/content` 패키지(30종)가 아래 확장 지점들로 구현되었다. 코어에 추가된 것은
**범용 규칙·이벤트뿐**이며, 증강별 하드코딩은 없다.

- **역 레지스트리 접근**: `ctx.yaku?: YakuRegistry` — 커스텀 역 등록/교체
  (`installAugment(engine, def, holder, { yaku })`; DraftController·ReplayReader가 전달).
  보유자 판별은 `WinContext.winnerId` + content의 `yakuHolders(yaku, id)` 패턴.
- **조커(만능패)**: `scoring.wildKinds` — 여기 실린 종류의 패는 **손패에서 무엇이든 된다**.
  `decompose`가 조커 자리를 실제 패로 바꾼 손을 전부 만들어 분해하고, `scoringOptionsOf`가
  같은 옵션을 화료·텐파이·대기·후리텐에 흘린다. 무엇이 될지는 고르지 않고 `evaluateWin`이
  변형 전부를 재서 **가장 비싼 것**을 채택한다(조커). 도라는 물리적인 패로 세고,
  후로(치·펑·깡) 판정은 조커를 보지 않는다.
- **채점 변형 규칙**: `scoring.wrapRuns`(순환 슌쯔) / `scoring.totalSets`(5멘쯔) /
  `scoring.kokushiMeldAssist`(펑 국사) / `win.blockedYaku`(역 봉인) —
  `scoringOptionsOf`가 DecomposeOptions로 묶어 모든 판정 지점에 적용.
- **점수 훅**: `score.extraHan`(동적 추가 판) / `RoundSettledPayload.winInfos`
  (화료 상세 — Interceptor로 역만 무효화·본장 보너스 등) / `win.treatAsDealer`.
- **패 변형 이벤트**: `TileKindChanged` — kind·attrs 변경 (수패 통일, 아카도라 부여).
  난수를 소비하면 payload.prngState로 PRNG 상태를 되돌려 놓는다 (Issue 002의 실전 활용).
- **정보 채널**: `view:{pid}:{key}` / `view:*:{key}` augmentData 규약 → PlayerView.augmentView (09 §7.5).
- **기타 규칙**: `deal.handSize` / `turn.direction` / `discard.blockedKinds` /

# 7. 정산 순서와 무장해제 (2026-07-27, 60차)

증강 2종 조합 감사(**docs/21_AUGMENT_PAIR_AUDIT.md**)에서 나온 구조 문제 두 개를 고친 결과다.
조합 버그의 실측·근거는 21번 문서가 단일 진실이고, 여기엔 **엔진 계약**만 적는다.

## 7.1 정산 단계 — `settleStages.ts`가 단일 진실

`ROUND_SETTLED`의 `deltas`를 고쳐 쓰는 증강이 20종을 넘고, 이들은 전부 "지금 값을 읽어
고쳐 쓴다" — **교환법칙이 없다.** 그런데 실행 순서가 `(tier, 등록 순서)`였다:

- `tier`는 표시용 등급 폐기 후에도 silver 5·gold 16·prism 83으로 혼재했다. 그래서
  역만 방어술(gold)이 책임전가(prism)보다 **항상** 먼저 돌아, 아직 손실이 0인 시점에
  발동 조건을 못 만족했다 — "역만 완전 면역"이 **한 번도 작동하지 않았다.**
- 같은 tier끼리는 `installAugment` 호출 순서 = **드래프트 픽 순서**로 갈렸다.
  기생충 × 일확천금은 누가 먼저 픽했느냐로 결과가 3배 차이 났다.

**계약**:

- 정산 인터셉터는 **`content/util.ts`의 `settleInterceptor(ctx, stage, fn)` 로만** 등록한다.
  `ctx.interceptor(ROUND_SETTLED, …)`를 직접 부르면 다시 tier·픽 순서에 끌려간다.
- 단계는 `SETTLE_STAGE`(core `augment/settleStages.ts`) 8종:
  `Replace → Redistribute → Multiply → BankTopUp → Transfer → DrawPatch → Shield → Observe`.
  전부 같은 `SETTLE_LAYER`(Prism)에 모여 있어 **priority만으로 순서가 결정**된다.
- 배치 원칙: 배수(`Multiply`)는 뱅크 가산(`BankTopUp`)보다 **먼저**, 정액 이동(`Transfer`)은
  배수·가산 **뒤에**, 방어(`Shield`)는 **반드시 마지막**(어떤 경로로 생긴 손실이든 최종값을
  봐야 "완전 면역"이 참이 된다).
- `ctx.reaction`/`ctx.interceptor`에 `EffectOptions {layer?, priority?}` 3번째 인자가 생겼다.
  정산 외 이벤트에서도 여러 증강이 순서에 의존하면 같은 방식으로 못 박는다.
- **부호로 상태를 추정하지 않는다.** 승승장구는 `deltas[id] < 0`으로 노텐을 추정하다
  다른 유국 증강이 만든 음수에 오염됐다. 이제 `RoundSettledPayload.tenpaiPlayers`
  (엔진의 실제 집계)를 읽는다. 정산 payload에 판정 근거가 없으면 **payload를 늘린다** —
  추정으로 메우면 조합에서 반드시 깨진다.

## 7.2 무장해제 — 규칙·효과·버튼·물리 상태 전부

예전 무장해제는 `RuleRegistry`/`EffectRegistry`의 source만 게이팅해 두 구멍이 있었다.

- **① 액티브 버튼이 안 잠겼다** → `installAugment`가 `holderTurnOptions`를 무장해제
  게이트(`isSourceDisarmed`)로 감싼다. 잠긴 증강은 후보가 비고, `FlowController.submit`이
  제시되지 않은 옵션을 거부하므로 액션까지 함께 막힌다. 규칙·효과를 하나도 등록하지 않는
  **순수 액션형 26종**(연금술사·개벽·거신병·단색 세계·재장전 …)이 이제 실제로 잠긴다.
- **② 이미 만들어 둔 물리 상태가 안 돌아왔다** → 무장해제는 잠그기 **직전에**
  `AugmentDisarmed { target, augmentId, source }`를 먼저 낸다. 대상 증강이 그 이벤트에
  반응해 스스로 원상복구한다.
  **⚠ 순서가 계약이다** — `DISARMED_SOURCES_KEY` 갱신을 먼저 두면 대상 증강의
  Reaction까지 꺼져 복구가 실행되지 않는다.
  선례: `true_dragon`이 손패에서 **가장 쓸모없는 3장**(같은 패·슌쯔 이웃 수로 결정적 채점,
  쯔모패 제외)을 **패산 맨 밑**으로 반납해 13/14장으로 돌아온다. 바닥이 아니라 패산인 이유는
  없던 방총·후리텐이 생기고 `discardedKinds`가 오염되기 때문이며, 애초에 배패에서 3장을 더
  받았으므로 그 국의 총 쯔모 수도 표준으로 정확히 복원된다.

**새 증강이 국 시작 시점에 물리 상태를 확정한다면**(배패 장수·좌석·후로 구성 등)
`AUGMENT_DISARMED` 반응을 함께 구현한다. 없으면 무장해제가 그 증강 보유자의 국을
성립 불가능한 상태로 만든다.

## 7.3 대기 계산의 단일 진실 — `PlayerView.scoringOptions`

봇 정책과 클라이언트는 `GameState`·`RuleRegistry`를 못 보므로 `scoringOptionsOf`를 부를 수
없어, 화료형을 바꾸는 증강(진짜 용 5멘쯔·무너진 국경·끝없는 윤회 …) 보유자의 대기를
표준 4멘쯔로 계산하고 있었다. `PlayerView.scoringOptions`에 뷰어 본인의 분해 옵션을 실어
`winningKinds(kinds, meldCount, undefined, view.scoringOptions)`로 넘기면 된다
(`scoringOptionsOf`는 `sequenceSuits`를 채우지 않아 JSON 직렬화에 안전하다).

## 7.4 봉인·잠금은 **상태에서 파생**한다 (해제 이벤트를 구독하지 않는다)

리치 봉인(`riichi_seal`)은 "한 번 세우면 그 국 내내 유지되는 플래그"였다. 그래서
공성계로 가짜 리치를 걸어 봉인만 세우고 손바닥 뒤집기로 취소해도 봉인이 남았다 —
아무 대가 없이 상대 셋의 리치를 지우는 조합(docs/21 §B-3).

2026-07-27부터 봉인은 **보유자가 그 리치를 지고 있는 동안만** 유효하다. 구현에서 중요한 것은
"해제 이벤트를 잡지 않았다"는 점이다:

- 플래그(`roundKey` 스코프)는 **과거 사실**만 기록한다 — "내 이번 국 리치가 첫 리치였다".
- 지금 유효한가는 **살아 있는 상태**에서 계산한다 — 보유자가 리치 중인가, 남이 리치 중인가.

손바닥 뒤집기(`RiichiFlipped`)든 승부수(`RiichiCanceled`)든 결국
`byPlayer[holder].riichi = null`로 끝나므로, 상태만 보면 **새 해제 수단이 생겨도 자동으로
따라온다.** 증강끼리 이벤트 이름을 알아야 하는 결합이 생기지 않는다.

**규칙**: "X 하는 동안 잠긴다"류 효과는 잠금 시점에 불리언을 굳히지 말고, 잠금 조건을
매번 상태에서 다시 계산한다. 그리고 **전원 공개 배너도 함께 동기화**한다 — 풀렸는데 배너가
남으면 상대가 걸 수 있는데도 안 거는 잘못된 대응을 한다(Rule #4는 정보가 **맞을** 때만 산다).

회귀: `packages/content/test/pair_fixes_60.test.ts`.

# 8. 남은 과제

- **커스텀 Zone·새 페이즈 증강**: 원시 기능(Zone·phase 데이터화)은 이미 있으나,

  새 선택지를 넣는 증강은 유사한 reactionOptions 훅이 필요하다.

  후보 열거 방식이라 조합 폭발이 난다. 현재는 무작위 선정으로 대체 —
  클라이언트 다중 선택 → 서버 검증 경로가 생기면 확장.
