# 36. 증강 예시 화면 — 설계 계획 (2026-08-19)

> **상태: 계획.** 이 문서에는 **아직 구현하지 않은 것**이 적혀 있다. 구현은 별도 작업으로 한다.
> **선행 작업(이미 반영됨)** — 로그인 화면에서 «증강 예시» 패널과 «규칙» 버튼을 걷어내고, 로고 + 로그인 상자만 가운데 한 상자로 세웠다. 그때 지운 데이터·CSS의 원본은 §7에 남겨 두었다.
> **관계** — [35_CLIENT_SHELL_2026-08-19.md](35_CLIENT_SHELL_2026-08-19.md)의 판 밖 화면 시각 규약을 그대로 따른다. 증강의 규칙 원문은 [10_AUGMENT_SYSTEM.md](10_AUGMENT_SYSTEM.md), 구현은 `packages/content/src/augments/`.

## 0. 왜 만드는가

사용자 지시 (2026-08-19):

> "예시랑 룰은 따로 빼서 조금 더 상세하게 **모든 증강의 예시**를 볼 수 있게 할 거야. 지금처럼 간략한 설명으로 모든 증강 예시를 **스크롤해서** 볼 수 있게."

지금 이 게임에서 "증강이 무엇을 하는가"를 알 수 있는 곳은 셋인데, 셋 다 **그림이 없다**:

| 자리 | 보이는 것 | 한계 |
|---|---|---|
| 드래프트 카드 (판 위) | 요약 + 설명 | 몇 초 안에 골라야 한다. 읽을 시간이 없다 |
| 증강 도감 | 요약 + 상세 (글) | 117종이 전부 **글**이다. "슌쯔의 무늬 제한이 사라진다"를 마작 초심자가 그릴 수 있나 |
| 규칙·도움말 | 마작 규칙 (그림 있음) | 증강은 다루지 않는다 |

로그인 화면에 있던 세 종짜리 «증강 예시»만이 유일하게 **패 그림으로** 말하고 있었다 — 그리고 그 셋은 로그인 전에 잠깐 스쳐 가는 자리에 있어서, 정작 증강을 고르기 시작한 사람은 다시 볼 수 없었다. 이 화면은 그 문법(**바뀌기 전 → 바뀐 뒤**)을 117종 전부로 넓히고, 로그인 뒤 언제든 열리는 자리로 옮기는 일이다.

### 이 화면이 아닌 것

- **도감이 아니다.** 도감은 "내가 무엇을 모았나 · 승률이 어떤가"(수집률·서버 평균순위·픽률)를 본다. 여기는 통계가 없다. **무슨 일이 일어나는지**만 본다.
- **규칙서가 아니다.** 조건·예외·우선순위는 도감 상세(`AugmentDef.detail`)의 몫이다. 여기 한 줄이 원문과 어긋나면 **여기를 고치는 게 아니라 지운다**(§4-9).
- **광고가 아니다.** 없는 기능을 그리지 않는다. 그림은 도움말과 **같은 컴포넌트·같은 에셋**을 쓴다.

## 1. 만드는 것 / 안 만드는 것

| | |
|---|---|
| **만든다** | 117종 전부가 한 화면에 세로로 늘어서고, 각 줄에 **한 줄 요약 + 그림 예시 한 개**가 붙는다. 계열 필터·검색으로 좁힐 수 있다. |
| **안 만든다** | 종별 상세 페이지(도감이 이미 한다) · 통계 · 시뮬레이터 · 애니메이션 · 증강 조합(시너지) 안내 |

**규모의 현실** — 117종 × 그림 1개 = 예시 117개를 **사람이 하나씩 쓴다.** 자동 생성할 방법은 없다(설명문에서 패를 유도하는 것은 거짓말을 만드는 가장 빠른 길이다). 그래서 §5의 배정표가 이 문서의 본체이고, 구현은 그 표를 데이터로 옮겨 적는 일이다.

## 2. 어디에 사는가

### 2-1. 결론: **증강 도감의 세 번째 탭 «예시»**

도감(`CodexScreen`)에는 이미 `도감 | 전체 통계` 두 탭이 있다. 여기에 **«예시»를 첫 탭으로** 넣고, 상태 줄의 «도감» 버튼이 그대로 문이 된다.

왜 새 화면을 세우지 않는가:

1. **목록이 둘이 되면 어긋난다.** 증강이 추가·개명될 때 고쳐야 할 곳이 하나여야 한다. 도감은 서버 카탈로그(`AugmentCatalogEntry`)를 그대로 받아 그리므로 이름·계열이 늘 최신이다. 예시 탭도 같은 배열 위에 선다.
2. **검색·계열 필터·툴바가 이미 있다.** 117줄을 훑는 화면에 이건 필수인데, 새 화면을 세우면 같은 것을 다시 만든다.
3. **문이 늘지 않는다.** 상태 줄에 버튼이 하나 더 붙으면 «규칙 · 도감 · 예시»가 되는데, 처음 온 사람에게 도감과 예시의 차이는 안 읽힌다.

**대안(채택하지 않음)** — 독립 화면 `AugExamplesScreen` + 상태 줄 «예시» 버튼. 도감이 통계 화면으로 굳어 있어서 성격이 섞이지 않는다는 장점은 있지만, 위 1·2번 비용을 그대로 다시 문다. 만약 나중에 예시가 종당 여러 개로 늘어나 화면이 도감보다 무거워지면 그때 분리한다 — 데이터(`augmentExample.ts`)가 화면과 분리돼 있으므로 옮기는 비용은 낮다.

### 2-2. 탭 순서와 기본값

```
[ 예시 ] [ 도감 ] [ 전체 통계 ]
```

- **기본 탭은 «예시»**로 바꾼다. 지금 기본은 «도감»(카드 격자 + 수집 ✓)인데, 처음 온 사람이 가장 먼저 알아야 할 것은 자기 수집률이 아니다.
- ⚠ 단, 기본 탭을 바꾸면 «수집한 것만» 체크박스가 예시 탭에서 무슨 뜻인지 애매해진다 → §3-4 참고(예시 탭에서는 그 체크박스를 숨긴다).

### 2-3. 다른 자리에서 들어오는 문

| 어디서 | 무엇을 | 왜 |
|---|---|---|
| 상태 줄 «도감» | 예시 탭으로 연다 | 유일한 문 |
| 도감 카드 상세 오버레이 | «예시 보기» 링크 | 글을 읽다 막힌 사람이 그림으로 가는 길 |
| 드래프트 카드 | **넣지 않는다** | 판 위에서 화면을 벗어나게 하면 안 된다(시간 제한이 돈다) |
| 로그인 화면 | **넣지 않는다** | 이번 지시의 핵심이 그것이다 — 로그인 화면에는 로고와 로그인 상자만 |

## 3. 화면 사양

### 3-1. 한 줄의 모양

한 종 = **가로 한 줄**. 상자를 씌우지 않는다(줄 사이 헤어라인 하나). 카드 격자로 만들면 그림 크기가 제각각인 예시들이 억지로 같은 상자에 눌린다.

```
┌───────────────────────────────────────────────────────────────────────┐
│  단색 세계   [손패 조작] [동풍전1·반장전2]                              │
│  손패의 수패를 전부 한 무늬로 바꾼다. 숫자는 그대로, 국당 1회.           │
│                                                                       │
│   🀇 🀝 🀘   →   🀝 🀝 🀝        숫자는 그대로, 색만 통일               │
│  (1m 5p 9s)     (159p)                                                │
└───────────────────────────────────────────────────────────────────────┘
```

| 부분 | 내용 | 출처 |
|---|---|---|
| 이름 | 증강 이름 | 서버 카탈로그 (`entry.name`) |
| 계열 칩 | 점수/정보/손패 조작/… | 서버 카탈로그 (`entry.category`) — 색은 기존 `aug-cat-*` |
| 사용 배지 | "상시" · "매 국 1회" · … | `AUGMENT_BRIEF[id].use` |
| 요약 한 줄 | 60자 안쪽 | `AUGMENT_BRIEF[id].text` — **여기서 새로 쓰지 않는다** |
| 그림 | §4의 일곱 틀 중 하나 | **새 파일** `augmentExample.ts` |
| 캡션 | 그림이 무엇을 보여 준 것인지 못 박는 한 줄 | 같음 |

요약을 새로 쓰지 않는 것이 요점이다 — 같은 증강의 한 줄이 화면마다 다르면 그게 규칙 문서가 셋으로 갈라지는 시작이다.

### 3-2. 순서

**계열 → 이름 가나다순.** 계열 머리글은 스크롤에 붙는다(sticky). 무작위·픽률순은 쓰지 않는다 — 두 번째로 열었을 때 같은 자리에 없으면 훑기가 안 된다.

계열 순서는 기존 `AUGMENT_CATEGORIES` 순서를 그대로 쓴다: 점수 · 정보 · 손패 조작 · 화료형 · 후로 · 리치 · 수비 · 교란 · 기타.

### 3-3. 스크롤과 성능 (⚠ 실측 필요)

117줄 × 패 이미지 평균 6~8장 = **`<img>` 700~900개**. 지금 도감은 카드 117개에 이미지가 없어서 이 문제를 만난 적이 없다.

대책은 순서대로:

1. `content-visibility: auto` + `contain-intrinsic-size` 를 줄(`.augex-item`)에 건다 — 화면 밖 줄은 레이아웃·페인트를 건너뛴다.
2. `TileImg` 가 `loading="lazy"` 를 붙일 수 있는지 확인한다(현재 `<img>` 속성 확인 필요). 프리로드(`tileImageSrcOf` 전량 프리로드)와 충돌하지 않는지도 같이 본다.
3. 1·2로 모자라면 계열 단위 접기(기본은 펼침)로 간다. **가상 스크롤은 마지막 수단** — Ctrl+F가 죽는다.

기존 성능 가드 테스트(`a11yPerfGuards.test.ts`)에 이 화면 몫을 추가한다.

### 3-4. 툴바

- **검색** — 이름·요약을 훑는다. 도감의 `.codex-search`를 그대로 쓴다.
- **계열 필터** — 도감의 `.codex-cats` 칩을 그대로 쓴다.
- **«수집한 것만» 체크박스는 예시 탭에서 숨긴다.** 이 화면의 목적은 **아직 안 만난 증강**을 보는 것이다. 잠금(`codex-card-locked`)도 걸지 않는다 — 예시는 전부 공개다.

### 3-5. 접근성

- 그림은 장식이 아니라 내용이다. 각 예시는 `<figure>` + `<figcaption>`(= 캡션 한 줄)으로 낸다. 패 이미지 하나하나에 alt를 붙이지 않는다(11장이면 스크린리더가 11번 읽는다) — 그림 전체를 `role="img"` + `aria-label`("1만 5통 9삭이 1통 5통 9통으로 바뀐다")로 한 번에 읽힌다.
- 화살표(→ / ↓)는 CSS `::before` 로 넣는다. 폭에 따라 방향이 바뀌므로 글자를 마크업에 박지 않는다(로그인 화면의 기존 처리와 같다).
- ○/✕ 표식은 색으로만 말하지 않는다 — 글자 표식이 항상 앞에 선다(기존 `.help-fig-mark` 규약).

## 4. 예시 문법 — 일곱 틀

**틀을 일곱으로 못 박는 이유**: 117개를 자유 형식으로 그리면 117가지 다른 그림이 나오고, 세 개쯤 읽은 사람이 네 번째에서 다시 처음부터 읽는 법을 배워야 한다. 틀이 고정돼 있으면 **모양만 보고 무슨 종류의 변화인지** 먼저 안다.

| # | 틀 | 코드명 | 무엇을 그리나 | 몇 종 |
|---|---|---|---|---|
| 1 | **전후** | `swap` | 바뀌기 전 패 → 바뀐 뒤 패 | 31 |
| 2 | **판정** | `verdict` | ✕ 원래는 안 되는 모양 / ○ 이 증강이면 되는 모양 | 17 |
| 3 | **시야** | `sight` | 뒷면이던 것이 나에게만 열린다 (또는 그 반대) | 18 |
| 4 | **점수** | `score` | 계산 한 줄이 어떻게 달라지나 | 34 |
| 5 | **순서** | `order` | 국·순의 흐름 어디에서 일어나나 | 18 |
| 6 | **자리** | `seat` | 넷 중 누구에게 무엇이 가나 | 21 |
| 7 | **글만** | `text` | 그림이 거짓말이 될 때의 도피처 | 0 (원칙) |

(합이 139로 117을 넘는 것은 두 틀을 겹쳐 쓰는 종이 22개이기 때문이다 — §4-8.)

### 4-1. 전후 `swap` — 손패가 바뀐다

로그인 화면에서 쓰던 바로 그 문법이다. **왼쪽 = 바뀌기 전, 오른쪽 = 바뀐 뒤.** 좁으면 위아래로 쌓이고 화살표가 ↓ 로 바뀐다.

- 패는 **효과와 직접 상관있는 것만** 놓는다. 손패 13장을 다 그리면 어디가 바뀌었는지 안 보인다. 3~4장이 상한.
- 바뀐 패에는 기존 `tile-conjured` 표식을 쓰지 않는다 — 그건 판 위에서 "생성된 패"라는 다른 뜻이다. 여기서는 **위치**(오른쪽)가 이미 말한다.
- 예: 단색 세계 `1m 5p 9s` → `159p`

### 4-2. 판정 `verdict` — 되는가 안 되는가

화료형(shape)·후로(call) 계열의 기본 틀. **두 줄**이고, 순서가 고정이다:

```
✕  2m 3p 4s   (보통은 몸통이 아니다)
○  2m 3p 4s   무너진 국경 — 무늬가 달라도 한 몸통
```

- 같은 패를 두 번 그린다. 패가 달라지면 "규칙이 바뀌었다"가 아니라 "다른 손이다"로 읽힌다.
- ✕가 먼저다. 원래 규칙을 먼저 세워야 무엇이 풀렸는지 보인다.
- 기존 `HelpFigure`의 `mark: "ok" | "no"` 를 그대로 쓴다.

### 4-3. 시야 `sight` — 누구에게 보이나

정보(info) 계열의 기본 틀. **뒷면 → 앞면**, 그리고 **누구의 눈인지 반드시 적는다**.

```
남들:  🂠 🂠 🂠 🂠
나:    2m 5p 7s 발       투시 — 그 국 내내 나에게만
```

- 뒷면은 기존 `.tile-back-face` 를 쓴다(전용 에셋이 없다 — `public/tiles/` 에는 앞면 34종뿐).
- "나에게만"을 캡션에서 빼먹지 않는다. 이 계열 증강의 절반은 **남들에게는 아무 일도 일어나지 않는다**는 것이 요점이다.

### 4-4. 점수 `score` — 계산 한 줄

점수(scoring) 계열의 기본 틀. **패를 그리지 않는다.** 숫자 한 줄이다.

```
보통    리치 · 뒷도라 없음      8,000
숨은 칼날   +2판 · 뒷도라        16,000
```

- 왼쪽에 "보통"이 항상 선다(판정 틀의 ✕와 같은 이유).
- 숫자는 실제로 계산이 맞아야 한다 — §4-9의 검증 대상이다. **자신 없으면 판수만 적고 점수를 적지 않는다**(`+2판`은 늘 참, `16,000`은 조건이 붙는다).
- 배수형(일확천금 ×0.5~3, 판돈 굴리기 ×2→×3→×4)은 숫자 대신 배수 막대로 그린다.

### 4-5. 순서 `order` — 언제 일어나나

국의 흐름 위에 **켜지는 구간**을 칠한다. 눈금은 셋 중 하나로 고정한다:

- **순 눈금** — `1순 … 6순 … 18순` (박무·함구령·불가침 조약·뒤늦은 출진)
- **국 눈금** — `동1 … 동4 / 남1 … 남4` (대기만성·귀환·미련)
- **국면 눈금** — `배패 → 첫 타패 → 진행 → 해저 → 유국` (밥상 뒤엎기·해저의 지배자·뒤집힌 모래시계)

한 증강에 눈금 하나만 쓴다. 섞으면 시간 축이 두 개가 된다.

### 4-6. 자리 `seat` — 누구에게 가나

교란(disrupt) 계열의 기본 틀. **넷의 자리를 마름모로 놓고 화살표 하나**를 그린다. 판 위 실제 자리 배치(하가/대면/상가)와 **같은 방향**으로 그린다 — 여기서 방향이 다르면 판에 들어가서 다시 배운다.

```
        대면
   상가   ●   하가        덤터기 — 내 쯔모 화료를 지목한 한 명이 전부 낸다
        나 ─┐
            └→ 대면 (-8000)
```

- 사람은 이름이 아니라 **자리 이름**(나/하가/대면/상가)으로 부른다.
- "무작위 한 명"(눈먼 총알)은 화살표 셋을 점선으로 그린다.

### 4-7. 글만 `text` — 도피처

그림이 **원문보다 좁게 말하게 되는** 증강에 쓴다. 예: 조건이 셋 이상이거나, 판 전체에 걸리는 전역 규칙이라 어느 한 장면을 고르는 순간 거짓이 되는 것.

**이 계획에서는 `text`로 배정한 증강이 없다.** 그래도 틀을 두는 이유는, 구현 중에 "이건 그림으로 하면 거짓말이 된다"는 판단이 서면 **장식용 그림을 그리는 대신 여기로 내려보내라**는 규약이기 때문이다. 로그인 화면의 옛 예시가 딱 그 실패였다("패 세 장이 효과와 아무 상관 없는 장식이었다", 2026-08-18).

### 4-8. 틀을 겹쳐 쓰기

한 증강에 **최대 두 틀까지** 허용한다(세 개면 그건 그 증강 설명이 아니라 강의다). 겹칠 때는 순서가 고정이다: **자리 → 점수**, **시야 → 순서**, **전후 → 점수**. 원인이 왼쪽, 결과가 오른쪽이다.

### 4-9. 진실성 규칙 (구현 시 필수)

예시 하나를 쓸 때마다 **`packages/content/src/augments/<id>.ts` 의 실제 구현을 열어 확인한다.** 요약문에서 유추해서 쓰지 않는다. 요약은 60자로 줄이면서 조건을 떨어뜨린 문장이고, 그 떨어진 조건이 그림에서 되살아나면 그림이 거짓이 된다.

구체적으로 확인할 것:

1. **횟수·타이밍** — "매 국 1회"인가 "게임 1회"인가, 발동 창이 첫 순인가 아무 때나인가.
2. **누구에게 보이는가** — 나만인가, 전원 공개인가.
3. **점수 숫자** — §4-4의 숫자가 실제 계산과 맞는가. 안 맞으면 판수만 적는다.
4. **패 표기가 실제로 파싱되는가** — `parseHelpTiles` 는 잘못된 표기를 **조용히 빈 배열로 떨어뜨린다**(`App.tsx:7846`). 오타 하나면 그림이 통째로 사라지는데 에러는 없다 → §6의 테스트가 이걸 막는다.

## 6. 데이터와 테스트

### 6-1. 새 파일 `packages/client/src/augmentExample.ts`

`augmentBrief.ts` 와 같은 규약이다 — id를 키로 하는 한 덩어리, 화면은 이걸 읽기만 한다.

```ts
/** §4의 일곱 틀. 판별 필드는 `form`. */
export type AugmentExample =
  | { form: "swap";    before: string; after: string; cap: string; note?: string }
  | { form: "verdict"; tiles: string; noCap: string; okCap: string; cap: string }
  | { form: "sight";   hidden: string; shown: string; who: string; cap: string }
  | { form: "score";   base: [string, string]; with: [string, string]; cap: string }
  | { form: "order";   scale: "turn" | "round" | "phase"; from: number; to: number; cap: string }
  | { form: "seat";    from: Seat; to: Seat[]; mark: string; cap: string }
  | { form: "text";    cap: string };

/** 두 틀을 겹쳐 쓰는 종(§4-8) — 최대 2개. */
export type AugmentExampleSet = readonly [AugmentExample] | readonly [AugmentExample, AugmentExample];

export const AUGMENT_EXAMPLE: Record<string, AugmentExampleSet> = { … };
```

**요약문은 여기 넣지 않는다** — `AUGMENT_BRIEF` 를 그대로 읽는다(§3-1).

### 6-2. 테스트 `packages/client/test/augmentExample.test.ts`

`augmentBrief.test.ts` 와 같은 자리에 놓는다. 지킬 것:

1. **빠짐 없음** — `packages/content` 가 내보내는 모든 증강 id가 `AUGMENT_EXAMPLE` 에 있다. 새 증강이 추가되면 여기서 빨간불이 난다(이게 이 테스트를 만드는 첫째 이유다).
2. **남는 것 없음** — `AUGMENT_EXAMPLE` 에 있는 id가 전부 실제 증강이다(개명·삭제된 것이 남아 있지 않다).
3. **패 표기가 실제로 파싱된다** — 모든 `before/after/tiles/hidden/shown` 이 `parseHelpTiles` 로 **빈 배열이 아닌** 결과를 낸다. §4-9의 4번 함정을 막는 유일한 장치다.
4. **캡션 길이** — `cap` 은 40자 안쪽(요약 60자보다 짧아야 한다 — 캡션은 그림에 붙는 말이지 두 번째 설명이 아니다).
5. **틀 겹침은 2개까지**, 순서 규약(§4-8)을 지킨다.

### 6-3. 화면 컴포넌트

- `AugExampleFigure` — `AugmentExample` 하나를 받아 §4의 틀로 그린다. 패는 **반드시** 기존 `HelpTileGroups`/`TileImg` 를 쓴다(별도 에셋 금지).
- `AugExampleList` — 계열별로 묶어 세로로 흘린다. 검색·필터는 도감 상태를 그대로 쓴다.
- CSS 접두사는 **`.augex-`**. 로그인 화면에서 지운 `.landing-show-*` 를 되살려 쓰지 않는다 — 이름이 자리를 가리키면 다음에 또 옮길 때 같은 일이 반복된다.

## 7. 로그인 화면에서 걷어낸 것 (원본 보존)

구현 시 §5-3(단색 세계·개벽)·§5-5(사방치기)의 초안 대신 **이 검증된 데이터를 그대로** 쓴다. 이 셋은 실제 화면에 서 있던 것이라 표기가 파싱되는 것이 확인돼 있다.

```ts
// 옛 LANDING_SHOWCASE (App.tsx, 2026-08-18 ~ 2026-08-19)
{ name: "사방치기",   kind: "상시",   before: "46m",      after: "456m",
  cap: "누가 버린 5만이든 치",     desc: "치는 원래 왼쪽(상가) 사람의 버림패로만 됩니다." },
{ name: "단색 세계",  kind: "액티브", before: "1m 5p 9s", after: "159p",
  cap: "숫자는 그대로, 색만 통일", desc: "손패의 수패가 원하는 한 색으로 물듭니다." },
{ name: "개벽",       kind: "액티브", before: "3m 7p 2s", after: "123z",
  cap: "수패가 통째로 자패로",     desc: "손패의 수패는 자패로, 자패는 수패로 뒤집힙니다." },
```

⚠ 사방치기(`omni_chi`)는 §5-5에서 `seat` 틀로 배정했다. 위 `46m → 456m` 은 **치가 성립한다**는 것만 보이고 "누구의 버림패로든"이라는 핵심을 그리지 못한다(캡션이 글로 때우고 있었다). 구현 시 둘 중 하나를 고른다 — 배정표대로 `seat` 로 가거나, 위 그림에 `seat` 를 겹쳐 쓰거나(§4-8). **`swap` 단독으로 두지는 않는다.**

같이 지운 것:
- CSS `.landing-show-*` 전량, `.panel-meta`(쓰는 곳이 이 패널뿐이었다)
- `.landing` 2단 격자와 `@container ui` 접기 규칙 두 개 → 가운데 한 상자(`max-width: 380px`, `margin: auto`)로 대체
- 로그인 상태 줄의 «규칙» 버튼 (`AuthScreen.onOpenHelp` prop 포함) — 로그인 뒤 상태 줄에 같은 버튼이 이미 있다

## 8. 구현 순서

한 번에 117개를 쓰지 않는다. **틀이 실제로 버티는지**를 먼저 확인하고 늘린다.

| 단계 | 내용 | 끝났다고 말할 수 있는 조건 |
|---|---|---|
| 1 | 틀 7종의 컴포넌트 + CSS(`.augex-*`) | 한 종씩 총 7개를 손으로 넣어 화면에 그려진다. 좁은 폭에서 화살표 방향이 뒤집힌다 |
| 2 | 도감에 «예시» 탭 추가, 목록 뼈대 | 117줄이 계열별로 서고 검색·필터가 돈다 (그림은 아직 비어 있어도 된다) |
| 3 | 데이터 채우기 — **계열 하나씩** | 계열 하나 끝날 때마다 §4-9 대조. shape(16) → hand(23) → info(9) 순서를 권한다 (틀이 가장 단순한 것부터) |
| 4 | 테스트(§6-2) | 빠짐 0 · 파싱 실패 0 |
| 5 | 성능(§3-3) | 실측: 첫 페인트, 스크롤 프레임. 가드 테스트 추가 |
| 6 | 도감 상세 → «예시 보기» 링크 | |

3단계는 **여러 세션에 나눠도 되게** 설계한다 — 테스트 1번(빠짐 없음)을 처음부터 켜 두면 남은 개수가 실패 메시지로 보인다.

## 9. 아직 안 정한 것

1. **`seat` 틀의 그림을 무엇으로 그리나** — 판 위의 좌석 컴포넌트를 재사용할지, 이 화면 전용 미니 마름모를 새로 그릴지. 재사용이 원칙이지만 판 위 것은 점수·바람·리치봉까지 달고 있어 예시로는 과하다. **1단계에서 결정**한다.
2. **`order` 틀의 눈금 길이** — 18순 눈금을 실제 18칸으로 그릴지, 구간만 표시할지.
3. **`score` 틀에 실제 점수를 얼마나 적을지** — §4-4는 "자신 없으면 판수만"이라고 정했지만, 그러면 점수 계열 21종 중 절반이 숫자 없는 그림이 된다. 3단계에서 점수 계열을 쓸 때 재검토.
4. **모바일에서 117줄** — 계열 접기를 기본값으로 할지. 3-3의 실측 뒤에 정한다.
5. **다국어** — 지금은 한국어뿐이라 문제가 없지만, 예시 문구가 117 × 2줄이면 나중에 가장 큰 번역 덩어리가 된다. 데이터를 화면과 분리해 두는 것(§6-1)이 그 대비다.
