**P8(conjured 패의 136장 보존) — 확인 완료. 2026-08-04 사용자 확정으로 종결.**

결론: **생성패가 4장 한도를 넘는 것은 프리즘의 의도된 상식 파괴다**(유지). 대신 봇의
장 세기만 사람과 같은 기준으로 맞췄다(#106).

근거 세 가지:
1. **사람에게는 이미 공개 정보다.** 생성패는 `attrs.conjured` → 클라 `.tile-conjured`
   (보라 글로우 + 반짝임)로 그려지고, 바닥(River)도 같은 `TileImg`를 쓰며 `PlayerView`가
   `attrs`를 그대로 실어 보낸다. 즉 바닥에 놓인 5번째 장은 **전원에게 "증강이 만든 패"로
   표시된다** — 감사가 상정한 "상대가 진짜 패로 착각해 패 셈이 무너진다"는 성립하지 않는다.
2. **코드가 이미 의도라고 적어 두었다.** `cliff_bloom.ts`: "4장 한도를 넘는 패가 생길 수
   있다 — 프리즘의 상식 파괴".
3. **발생 조건이 "자기가 만든 화료를 스스로 거절"이다.** 이 증강들은 전부 화료시키려고
   패를 만든다. 봇은 화료를 100% 누른다.

남아 있던 실제 결함은 **봇만 생성패를 진짜 패로 셌다**는 것 하나였고, `tileTracker`가
`conjured`를 제외하도록 고쳤다(#106). 현물·스지 판정(`readThreats`)은 그대로 둔다 —
생성패라도 바닥에 놓인 이상 그 사람은 그 종류로 론할 수 없다(후리텐).

봉인(`discard.blockedTileIds`)을 도입하지 않은 이유는 아래 표 참조 — 깔끔히 통하는 것은
`void_kan` 하나뿐인데 그 증강의 명시된 "무페널티(대가 없음)" 원칙을 깨야 하고,
`off_by_one`은 리치 중 봉인 우회라 애초에 막히지 않으며, `cliff_bloom`·`regret`은
전량 봉인이 소프트락이다.

| 증강 | 생성패가 가는 곳 | 바닥에 도달하는 조건 | `discard.blockedTileIds` 봉인으로 막히나 |
|---|---|---|---|
| `bluff_pretense` | 후로(멜드) | 파혼(`meld_dissolve`)이 그 펑을 풀면 손패로 돌아와 버려질 수 있다 | 단독으로 다룰 사안 아님 |
| `void_kan` | 손패 1장 | 챤깡을 거절하면 국 내내 | ⭕ 되지만 이 증강의 "무페널티(대가 없음)" 설계와 충돌 |
| `haitei_lord` | 해저패(쯔모패) | 화료를 거절하면 | 리치가 아니면 ⭕ / 리치 중이면 ❌ |
| `off_by_one` | 쯔모패 (리치 전용) | 화료를 거절하면 | ❌ — 리치 중에는 코어가 봉인을 건너뛴다(선언패만 버릴 수 있어야 하므로) |
| `cliff_bloom` | 손패 **전체**(만개) | 즉시 화료 안 하면 | ❌ 전량 봉인 = 소프트락 |
| `regret` | 다음 국 배패 **13장** | 국 내내 | ❌ 전량 봉인 = 소프트락 |

장래에 이 결정을 뒤집는다면 유일하게 온전한 길은 `suit_unify`가 이미 간 방식 —
kind 덮어쓰기를 **실물 교환**으로 바꾸는 재설계다. 4종을 다시 짜야 하고, 실물을 왕패·
패산에서 끌어오므로 유국 타이밍·해저가 밀린다는 대가가 따른다.

**P5(`discardedKinds`를 턴 카운터로 쓴다) — 전수 확인 완료. #107에서 종결.**

감사는 4종으로 적었지만 **실제로는 13종**이었다(소스 스캔으로 전수 확인). 근본 원인은
필드 하나가 두 가지 일을 겸한 것이다 — `discardedKinds`는 *후리텐 이력*이라 누명이면
지목당한 사람 쪽에 새겨지고, 거신병·미래를 보는 자는 이 목록을 통째로 다시 쓴다.

`PlayerRoundState.discardCount`(실제 버림 횟수, `creditTo` 무관)를 코어에 추가하고
13종을 전부 옮겼다. `helper_contracts.test.ts`가 `discardedKinds.length` 직접 사용을
금지해 재발을 막는다.

## 3. 권장 착수 순서

**1단계 — 안전망 (다른 수정을 안전하게 만드는 것)**
1. 훅 예외 격리 (`EventProcessor` source별 try/catch + `HanchanController` 국 단위 격리)
2. `RuleContext.state` 필수화 또는 `sourceGate`를 state 부재 시 **거부**로 반전
3. `conflicts` 전수 선언 (docs/21의 ✅ 아닌 행 전부)

**2단계 — 공용 헬퍼 봉합 (P1~P3, P7~P9)**
`stripRed()` / `clearDrawFlags()` / `riichiHidden` 강제 / `widenPeek` 강제 / `withAugPoint` 강제.
각각 **소스 스캔 테스트**를 함께 추가해 사본이 다시 생기지 않게 할 것 — 이 감사에서 나온 결함의 절반이 "한 파일에서 고쳤는데 형제 파일에 안 퍼진 것"이다.

**3단계 — 점수 정합성**
리치 공탁 실납부액 기록 / `markPassFuriten` 예외 / 커스텀 역 `source` 인스턴스화 / 정산 stage 동률 결정적 정렬 / `rebuildAugments` 순서 복원

**4단계 — 개별 결함**
카테고리별 표 순서대로.

**5단계 — 봇·밸런스**
파워 티어 가중 배선 / 봇 드래프트 가중 선택 / 봇 발동 우선순위(`{option, weight}`) / 봇 자해 정책 4종

## 4. 감사 방법

카테고리별 서브에이전트 8기를 병렬 실행했다. 각 팀에 준 제약:
- 기존 테스트 994개는 전부 통과하므로 **테스트 사각지대만** 노릴 것
- `docs/21`·`docs/22` 기재 항목은 중복 보고 금지
- 모든 발견에 `file:line` 근거 + 구체적 재현 시나리오 + 확신도 필수, 추측성 지적 금지

**교차 확인**: 커스텀 역 `source` 문제는 4개 팀이 서로 모른 채 독립 발견했고, 정산 stage 동률 문제는 3개 팀이 서로 다른 그룹(Shield/Transfer/Multiply)에서 발견했다. `markPassFuriten` 문제도 2개 팀이 서로 다른 증강에서 짚었다. 이 세 건은 개별 증강 버그가 아니라 **코어 계약의 구멍**으로 취급해야 한다.
